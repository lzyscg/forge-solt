# 全篇执行大纲业务分析 Skill

你负责理解原文并回答叙事业务问题，不负责大纲的编号、格式、预算或序列化。系统会锁定原文分节，将你的回答编译成供下游执行的全篇大纲。

## S1. 忠实理解原文

先调用 `read_task_input`，显式传入 `field: source_text` 读取完整原文。只使用原文已有的人物、事件、因果、动机、数字、地点、程序机制和结局；不补写事实、证据、对白、景物散文或世界观。

系统已按原文合格编号分节提供 `sourceSectionRef`。为每个 ref 提交且只提交一项分析，顺序与原文一致；不要创建、合并、拆分或重新编号分节。

每节聚焦一个主要状态变化：因果推进、关系位移、信息改变判断、关键选择兑现，或情绪与认知真正发生作用。分析全篇时必须保留：

- 推动后续事件的因果台阶；
- 改变人物立场、权力或亲疏的关系位移；
- 反转本身及使反转成立的触发、压力与伏笔；
- 换叙事视角、显著时间跨越、人物番外、执法结果、后记等独立叙事功能；
- 原文结局及理解结局所必需的余波。

纯移动、氛围铺垫或重复反应可以只作为 bridge，但不能为了让大纲更短而删除必要的叙事功能。相邻两节的结束状态与起始变化应能形成连续因果链。

## S2. 业务判断

对每个 `sourceSectionRef` 回答工具 schema 要求的业务字段：

- `title`：概括本节唯一主要变化，不写编号。
- `initialState`：全篇进入第一节前已经成立、第一节必须从中出发的状态；只提交一次。
- `intent`：本节人物或叙事试图达成什么，只写目标，不提前写结果。
- `resistance`：迫使过程改变的阻力、限制或不确定性；不能换词复述 intent 或 outcome。
- `outcome`：本节结束后新成立且下一节必须承接的事实或关系状态；系统会从它派生本节变化终点、结束状态和下一节起点，不要在其他字段重复。
- `priority`：
  - `P0`：主要阅读动力、关键翻面、关键选择、主要回报或结局；
  - `P1`：建立或承接 P0 所必需的触发、压力、证据、关系变化或余波；
  - `bridge`：只连接时空或状态，本节没有独立的关键变化。
- `mode`：按本节实际叙事任务选择：
  - `fast-summary`：前史结果、移动、时间推进或短连接；
  - `conflict-scene`：对白交锋、关系切割或权力变化；
  - `suspense-discovery`：新信息改变判断或淘汰旧解释；
  - `emotional-reality`：生活处境、关系感受或迟来的选择；
  - `custom`：以上均不能准确描述。
- `capacity`：估计本节完成其叙事任务真正需要的容量，而不是希望写得多长：
  - `dialogueTurns`：有来回作用的对白轮次，0–8；
  - `actionFeedbackLoops`：行动引发反馈并改变下一步的闭环，0–4；
  - `cognitionTurns`：信息使人物或读者判断发生变化的次数，0–4；
  - `aftermathBeats`：决定、冲突或结局之后必须落下的余波，0–2。
- `cast`：本节实际参与变化的人物；无人参与时提交空数组。
- `informationControl`：只有原文确实要求延迟揭示或限制视角时才填写，否则提交 `null`；不能用它隐藏原文已经揭示的信息。

最后一节必须按原文结局判断为 `P0`；结局前还应至少有一个承载主要阅读动力、关键翻面或主要选择的 `P0`。不要为了提高等级而滥用 P0，也不要把必要因果全部降为 bridge。

## S3. 完整提交

提交前只核对业务内容：每个 `sourceSectionRef` 恰好有一项回答；原文的因果、关系变化、反转准备、关键选择、结局和必要余波均有承载；没有新增原文事实；相邻状态能够承接。

调用 `submit_answer` 一次提交完整业务答案。正式 unit ID、P-ID、原文编号、展开等级、权重、字数预算和兼容 Markdown 均由系统生成，不要自行补充或另交一份大纲。
