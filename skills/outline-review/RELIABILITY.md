# outline-review 判据的来源与可靠度（D-28 要求的记录）

> **为什么这份记录不在 `SKILL.md` 里。**
> `SKILL.md` 的每一个字节都会进模型上下文：frontmatter 之后、首个 `## S<n>` 之前的
> 全部内容进 preamble，由 `context-builder.ts` 的 `buildReviewSlotTexts` 注入 system prompt。
> 把「这条判据可能没用」写进去，等于在审核时先给模型一个放行的理由。
> 所以记录放在这里——同一个目录，人看得到，模型看不到。
> 与 `skills/scene-review/RELIABILITY.md` 同一条纪律。

## 第一次真实模型实测（2026-08-28，任务「骨架审核首跑」）

模型 `deepseek-chat`（= deepseek-v4-flash），DeepSeek 官方，全程一次通过，任务约 4 分钟。

**结果：四条判据全部未检出，0 检出。**

| 判据 | 裁决 | 人工复核 |
|---|---|---|
| S1 四项齐全 | 未检出 | **判对了**。三条场景的出场/目标/冲突/结束状态都写全了 |
| S2 只写规划 | 未检出 | **判对了**。无对白、无景物白描（有一处引号内的「要传达的意思」，是转述不是台词，属边界内） |
| S3 结束状态接得上 | 未检出 | **判对了**。一→二（决定连夜核对 → 连夜核对）、二→三（翻出物件 → 对照证据）都接得上 |
| S4 条目与槽位一一对应 | 未检出 | **判对了**。骨架 3 条场景，结构 3 个场景槽位 |

四条**全是真阴性**——我逐条对着骨架原文复核过，这一份骨架确实没有这四类问题。

### 这次跑证明了什么、没证明什么

**证明了**：链路在真实模型下通；四条判据在一份合格骨架上**不误报**。
不误报有实际价值——一次误报就是一整轮无谓返修（4 次审核 + 1 次重写）。

**没证明**：召回。这一跑里骨架本身是干净的，所以「判据能不能抓住坏骨架」
**一个字都没验到**。要验召回，得拿一份**故意写坏**的骨架跑
（缺字段 / 混对白 / 条数对不上），那是下一次要做的事。

设计阶段用的那份样本（见下节）上三条会检出，但那是我人工比对的结果，
不是模型的判定——两者不能混为一谈。

## 判据文本的出处（实施文档 §6.3：直接取自写作 Skill，不另写一套标准）

| 审核判据 | 取自 `skills/outline-writing/SKILL.md` |
|---|---|
| S1 每个场景条目都写全出场、目标、冲突、结束状态四项 | S1「这份骨架要回答什么」四问全节 + S3 自检项第 2 条 |
| S2 只写规划，不写正文 | S2「写法」末段（不要写对白/景物/替下游想句子）+ S3 自检项第 4 条 |
| S3 相邻两条的「结束状态」接得上下一条的开场 | S3 自检项第 3 条 |
| S4 场景条目与结构里的场景槽位一一对应 | S3 自检项第 1 条 |

S1 的内容与 `templates/zhihu-chapter/template.yaml` 中 `chapter_outline` 的 `guidance`
第一条对应（「每个场景需明确写出目标、冲突与出场人物」），S2 与第二条对应
（「只写规划，不写正文散文」）。

## 设计时用的唯一一份真实样本（N=1）

判据不是凭空写的，但样本只有一份：`data/forge-core.sqlite` 里任务
「《深夜来电》第三章」产出的骨架。对着 `outline-writing` 的自检表逐条比，
那一份骨架上能看出两处硬伤、一处存疑：

| 判据 | 在这份样本上 | 具体 |
|---|---|---|
| S1 | **会检出** | `标题 · 深夜来电` 这一条缺「出场」字段 |
| S2 | **会检出** | 场景二写着 `「我藏了……」「别查……盯……」`，是对白 |
| S3 | 不检出 | 四条的结束状态与下一条开场都接得上 |
| S4 | **会检出** | `标题 · 深夜来电` 不是场景条目，结构里没有槽位与它对应 |

N=1，不能当召回率读。它只说明这四条判据**不是全都指向空处**——
这比 scene-review 的 S3/S4 在设计阶段的处境好一点，但也仅此而已。

## 三处与 scene-review 不同的设计决定

**1. 每条判据都写明「引哪一句」。**
D-11 的引文闸门要求每条 finding 带一句逐字出自正文的引文，核对不上就丢弃。
丢弃是最坏的结果：既花了一次调用，检出的问题又被静默吞掉（verdict 记 `discarded`，
对下游等同未检出）。骨架判据里有两条天然缺引文锚点——
S4 说的是「条数对不上」，那是一个计数而不是一句话；S1 说的是「缺了某字段」，
缺失的东西引不出来。所以每条判据末尾都直接指定引哪一行
（S4 引多余条目的标题行，S1 引缺字段那条的标题行）。

**2. S1 与 S4 的范围被刻意切开。**
两条都会在「多出来一个非场景条目」上触发。S1 因此限定「只检查形如
`场景 N · 某某` 的场景条目」，把非场景条目整个让给 S4。
切法只能靠**限定自己的范围**，不能写「这归 S4 管」——
D-23 要求一次调用的 prompt 里不出现其他判据，写了就违反。

**3. `maxRevisionRounds: 1`，比 scene 少一轮。**
scene 是散文，实测改一轮会带出新问题（S2 连着三轮都在报，且每轮引的是不同的句子）。
骨架是清单，「缺字段 / 写了对白 / 条数对不上」一稿就该改干净；
改两轮还在报，说明是判据或 instruction 有问题，不是再来一轮能解决的。

**这个数字同样没有实测支撑**，它是从「骨架是清单不是散文」推出来的。
如果第一次真实跑里出现「第 2 稿仍被检出且检出的是新问题」，就该回来改这个数。

## 成本

骨架比场景短（`minChars: 100` / `maxChars: 3000`，实测样本约 1.5k 字符），
单次审核调用的输入应当明显小于场景审核（实测场景审核 7k–15k input tokens）。
但**调用次数一样**：4 条判据 × 最多 2 稿 = 最多 8 次。

这笔钱买的是「在上游拦住」：骨架错了，下游每一个场景槽位都跟着错，
而那时全部写作 token 已经花完。实测样本里一个章节有 4 个场景槽位——
在骨架上多花一轮，比在 4 个场景上各返修一轮便宜。

**这条推理也还没有数据。** 它成立的前提是「骨架的错真的会传导到场景」，
而那需要一次对照实验才能证实：同一份输入，开与不开骨架审核各跑一次，
比较场景的返修轮次总和。
