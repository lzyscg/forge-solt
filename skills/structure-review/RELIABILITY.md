# structure-review 判据的来源与可靠度（D-28 要求的记录）

> **为什么这份记录不在 `SKILL.md` 里。**
> `SKILL.md` 的每一个字节都会进模型上下文：frontmatter 之后、首个 `## S<n>` 之前的
> 全部内容进 preamble，由 `context-builder.ts` 的 `buildReviewSlotTexts` 注入 system prompt。
> 把「这条判据可能没用」写进去，等于在审核时先给模型一个放行的理由。
> 所以记录放在这里——同一个目录，人看得到，模型看不到。
> 与 `skills/scene-review/RELIABILITY.md`、`skills/outline-review/RELIABILITY.md` 同一条纪律。

### S1 那一条：判据自己写错了，不是模型判错了

`title` 槽位的目标是：

> 拟定本章标题，取意「对账」——林越拿着半张收据来找当年经手的会计苏敏对清这笔钱的
> 去向，题眼落在取证与对质上。不出现小标题，只给出单章标题方向。

按 SKILL.md 里 S1 对短槽位那段的写法（「它的『停在哪里』是『读者看完标题应当得到
什么预期』」），这一条**没有**写「停在哪里」。严格照判据，它该被检出。

但模型放过它是**合理的**：标题根本没有「停在哪里」这个概念。
那段类比是我为了让 S1 覆盖 title 硬造的映射，造得很牵强——
真按它执行，代价是每次都因为一个不存在的字段把整棵结构打回重来。

所以这不算模型的漏报，算**判据的设计缺陷**。两个改法：

1. S1 明确限定只检查「有下游正文要写、且需要与前后衔接」的槽位，把 title 排除掉；
2. 或者给 title 单独一条判据（「标题的目标是否说清了它要概括什么」）。

**已按第 1 种改（2026-08-28，`structure-review` 1.0.0 → 1.1.0）**：
判据不在多，在每一条都指向真实存在的东西。

两点如实记下：

- 这次收窄**不影响任何已报数字**——S1 至今两跑合计 0 检出，分母里本来就没有
  靠 title 攒出来的数。这不是为了让数字好看而改判据（D-28）。
- 代价是**标题槽位现在没有任何判据覆盖**。这是已知空白，不是已解决的问题。

### 这次跑证明了什么、没证明什么

**证明了**：机制在真实模型下通——结构审核在任何槽位开工之前跑完并结算，

四条判据在一棵合格的结构上**不误报**，这有实际价值：一次误报就是整棵树重来。

**完全没证明**：

- **召回。** 这一跑的结构本身是干净的（我逐条对着执行包复核过），
  「判据能不能抓住一棵坏结构」一个字都没验到。
- **「每条判据写明引哪一句」这条设计。** 它要防的是 finding 被引文闸门丢弃，
  而这一跑**一条 finding 都没产生**（discarded = 0，分母也是 0）。
  这是骨架审核那次留下的同一个缺口，两次都没补上。
- **重来回路在真实模型下的行为。** 结构一次就过了，`maxRevisionRounds: 3`
  这个数、以及「重来会不会带出新问题」这个我最担心的点，全都没碰到。

**下次要做的是拿一份故意写坏的执行包跑**（缺停点 / 目标里写对白 / 漏掉点名的物件），

### 合并 outline **没有省 token**，反而贵了

这一条与我动工前的假设相反，记在这里免得下次又照着错的直觉决策。

拿同一份真实库里上一次带骨架槽位的跑（`149773d9`）对照**上游部分**：

| | 上跑（有骨架槽位） | 这跑（合并后） |
|---|---|---|
| 结构生成 | 12 906 | 12 682 |
| 骨架填槽 | 4 932 | — |
| 骨架审核（4 条） | 24 159 | — |
| 结构审核（4 条） | — | 36 359 |
| **上游合计** | **41 997 / 6 次** | **49 041 / 5 次** |

上游**贵了 7 044 输入 token（+16.8%）**，调用次数少一次。
原因是待审文本变长了：骨架是一个 1.5k 字符的槽位正文，
而结构概要要把整棵树每个槽位的目标全渲染出来。

标题那一槽也贵了：5 407 → 13 091（**+142%**）。这是合并的直接后果——
标题原先 `dependsOn` 骨架（读一份 1.5k 的规划），现在 `dependsOn` 全部场景（读全文）。
换来的是标题确实在概括正文而不是概括一份规划，这一跑产出的
「半张纸，对不上三年的账」比上一跑的标题贴题得多，但那是主观判断，不是数据。

**所以合并的收益不在 token，在别处**：同一件事不再被生成两遍、审两遍；
下游每次填槽不再被注入一份与 instruction 高度重复的骨架；
以及——这才是主要的——审核终于能审到**每个槽位各自的目标**，
而不是审一份与结构分离、可能已经和结构对不上的清单。
省钱这个理由不成立，别再用它。

## 第二次真实实测：故意写坏的执行包（2026-08-28，任务 `d4fda471`）

上一节末尾说「下次要拿一份故意写坏的执行包跑」。跑了。执行包见

| 施压手段 | 想诱发 |
|---|---|

- **S3**：三道缝的停点与起点逐字对得上（`scene_002` 开头写「接住上一场停点（小林等赵敏
  回应那一瞬）」，与 `scene_001` 的停点原文一致，另两道同样）。
- **S4**：十个点名项**全部有落点**，包括我埋在第 6 条、最容易整条忽略的「呼叫铃从头到尾
  没人关」——它在 `scene_001` 起、`scene_004` 收。

### 结论一：**「写一份坏执行包」这条路验不到结构审核的召回**

这是本次跑最重要的一条，它否掉的是我自己上一节定下的方法。

判据审的是**结构 Agent 写出来的目标**，而执行包只是它的输入。中间隔着一个 Agent，
输入端施压控制不了输出端。三个方向的压力全被扛住了，且不是运气——
`chapter-structure-design` 的 S5 自检明确要求逐项对账，它照做了。

**要验召回，只能把坏结构直接注进去**，跑真实审核那一段（约 4 次调用），
不要再整跑。整跑一次约 71 万输入 token，而它对召回这个问题的信息量是零。

### 结论二：S2 的判据文本有缺陷，模型比判据对

结构 Agent 写出来的 instruction 里**确实有引号包起来的人物台词**，三处：

> `scene_002`：家属说出执行包点名的原话"你们是不是觉得我爸不值得救"，
> 周医生必须原样回应"我没有这么说过，我说的是现在不能动"

按 S2「具体表现」第 1 类（「目标里出现**引号包起来的人物台词**」）与那句
「写成一句可以直接抄进正文的台词才算」，这**该被检出**。它没有。

但模型放行是对的：执行包硬性规定这几句一字不改，规划里不写清楚，下游就没法兑现。
**判据没有区分「Agent 自己编了对白」（替下游写了，是违规）与「Agent 转述了执行包的
硬约束」（把约束传下去，是本分）**，两者方向相反。

这是**同一个坑的第二次**——S1/title 那次也是判据指向了不该指的东西，模型没上当。
两跑两次，模型的判断都比判据准。**说明现在的瓶颈在判据文本，不在模型能力。**

**已改（2026-08-28，与 S1 那条一起，`structure-review` 1.0.0 → 1.1.0）**：
S2 加了一条例外——执行包**逐字指定**、要求原样出现的台词，转述进 instruction
不算违反，判断方法是回头对照【任务输入】里的执行包逐字比对；
但目标里要写明它出自执行包，别让下游误以为是规划者自拟的。

~~这条例外还没有被任何一次真跑验证过。~~
**已验（第三节，坏树注入）**：S2-a 树里的自拟对白被 S2 抓到，模型的问题描述
逐字引用了这条例外并主动说明它不适用；同一批里基线树那句真·执行包指定的台词
两跑都没被报。放行该放行的、抓住不该放行的，边界划对了。

## 第三次实测：**直接注入坏树**（2026-08-28，`probe/bad-tree-recall.ts`）

前两跑都验不到召回，原因写在上面：判据判的是结构 Agent 的**产出**，
从输入侧加压中间隔着一整个 Agent。这次绕开它——**把坏树直接喂进引擎**。

**方法**：跑的是真引擎（`createEngineHarness` + 仓库里的 templates/ 与 skills/），
结构设计 Agent 换成 FakeProvider 直接吐出我造的树，**只有结构审核那几次调用走真模型**。
不自己拼 prompt——结构审核的 prompt 里有渲染后的结构概要，手拼一份测的就不是
生产里真正发出去的那份，召回数字不转移。六棵树，每棵只动一处（单变量）。
判据文本是今天刚改过的 1.1.0。

| 树 | 植入 | 检出 | 复核 |
|---|---|---|---|
| clean | 无 | 无 | ✅ 无误报 |
| S1 | scene_02 不写停点 | **S1** | ✅ 真阳性 |
| S2-a | 自拟对白两句 | **S2** | ✅ 真阳性，见下 |
| clean-repeat | 无（与 clean 同树） | **S4** | ❌ **误报**，见下 |
| S3 | 停点与下一场开场之间跳掉一段 | **S3**, S4 | ✅ S3 真阳性；S4 误报 |
| S4 | 拿掉可承接的结尾状态 | **S4** | ✅ 真阳性 |

**召回 4/4，误报 2 条（都是 S4，同一个根因）。**

### 结论一：四条判据全部是活的

前两跑合计 0 检出，一度像是「判据写了但根本不работ」。不是。
**换个测法，四条全部命中各自的植入缺陷。** 前两跑测不到，是测法的问题，
不是判据的问题——这一点现在有对照组撑着说了。

### 结论二：今天加的 S2 例外**生效了，而且没有放宽过头**

这是本次最想验的一条。S2-a 里那两句是我自拟的、执行包里没有的对白，
模型的问题描述**逐字引用了新加的例外并主动说明它不适用**：

> 这句在执行包中没有任何逐字出处（执行包唯一逐字指定的是周桂芳的
> "晓晓的学费，你们谁管"），不适用例外。

同时，**基线树 scene_04 里那句真·执行包指定的台词，两跑都没被 S2 报**。
一边放行该放行的，一边抓住不该放行的——例外的边界划在了对的地方。

（上面那句「例外还没有被任何真跑验证过」的告警到此解除。写判据的人和复核的人
仍然是同一个，但这次至少有 A/B 对照，不是自己说自己对。）

### 结论三：**S4 的判据文本有缺陷，会在正确的树上误报**

两条误报的问题描述几乎一字不差，指向同一处：

> scene_04 …… 把执行包的原文改写成了省略「必须」和「具体的」的版本，
> **没有原样落到**最后一场的 instruction 中。

根因在判据引的规范原文那句「这一条要**原样**落到最后一场的 `instruction` 里」。
模型把「原样」读成了**逐字复制执行包那句话**。但基线树其实已经把状态本身
一字不差地写进去了（「分家会没有结论，但四房各自去做了一件事」），
少的只是「必须」「具体的」——那是**执行包描述要求时用的词，不是状态的一部分**。

改法（**还没做**）：把 S4 里的「原样落到」改成
「这个**状态本身**要能在某个槽位的目标里找到落点；执行包描述要求时用的措辞
（必须、具体的、一定要……）不算状态的一部分，不要求逐字复制」。

### 结论四：**同一棵树跑两次，裁决不一样**

`clean` 与 `clean-repeat` 是**同一棵树**。S4 一次未检出、一次检出。

所以上面的 4/4 得打折看：**它是单次观测，不是稳定行为。**
四条判据各只有 1 个植入样本，而已知至少有一条判据在同一输入上会翻面。
要说「S1 召回 x%」还差得远——现在能说的只是「这四条判据都能被触发」。

一致性检查是顺手加的（本来只是想复用同一棵树验 S2 例外），结果它是这一跑
最有价值的一条。以后每个探针都留一个重复样本。

### 我在这一跑里踩的坑，记下来

**审核执行失败不写 `slot_reviews`。** 于是「这条判据的调用根本没成功」
和「这条判据未检出问题」在裁决表里长得**完全一样**。

第一版探针按「调用次数」关花钱的闸门，而一次 runTurn 是 Agent 循环的
**一个 turn**（先 `read_structure_outline`，再 `complete_assignment`），
一条判据要好几个 turn。闸门于是在第一条判据就关了，S2/S3/S4 一次都没评到，
而我从裁决表里读出来的是「1/4 召回」——一个完全错误的结论，看起来却很合理。

现在探针把「第 0 轮是不是齐了 4 条裁决」钉成硬断言，不齐就整份结果标记不可信。
**任何读 `slot_reviews` 的分析都要先问这一句**，包括读生产库的那些。

## 判据文本的出处（实施文档 §6.3：直接取自写作 Skill，不另写一套标准）

| 审核判据 | 取自 `skills/chapter-structure-design/SKILL.md` |
|---|---|
| S1 目标写清「发生什么 / 建立或改变什么 / 停在哪里」 | S2 全节（含好坏对照那两条）+ S5 自检第 5 条 |
| S2 目标是规划，不是正文 | S4 反模式第 2 条「instruction 写成了正文」 |
| S3 相邻两场的停点与起点接得上 | S3 第 1 条链式依赖 + S5 自检第 10 条 |
| S4 执行包点名的东西都有槽位承载 | S1 第 3 条 + S4 反模式第 3 条「漏掉结尾状态」 |

四条都不与**确定性校验**重叠。`structure-validation.ts` 的 19 条规则管的是形式
（ID 唯一、根唯一且是容器、依赖不成环不指容器、深度与数量上限、instruction 非空、
至少一个内容槽位……），判据管的是**那几行中文写了什么**。
SKILL.md 里因此明写「已经通过确定性校验的事你不用管，也不要报」——
不写的话模型会去报「这个 ID 不够语义化」这类既无用又消耗一整轮返修的东西。

## 一条**没有**放进来的判据：场景粒度过细

`chapter-structure-design/SKILL.md` S4 把「把进门/落座/开口拆成三场」列在**第一位**，
它却没进这四条。理由：

1. **引不出证据。** D-11 的闸门要求 finding 带一句逐字出自待审文本的引文。
   粒度问题不在某一句话里，而在两条 instruction 的**关系**上，
   引哪一句都不构成「这两场应该合并」的证据。
2. **判断高度主观。** 三场还是两场，很多时候两可。
3. **误报的代价最大。** 别的判据误报只是多改一条目标；这一条误报是整棵树重来。

等 S1–S4 有了几次真实命中分布，再决定要不要补。

## 与骨架审核（`skills/outline-review`）的关系

骨架审核审的是一个**独立槽位的正文**——那个槽位已经从 `templates/zhihu-chapter`
里去掉了，因为它与结构生成做的是同一件事（划分场景 + 写清每场目标），
两遍生成、两遍审核、每次填槽再注入两遍。

`skills/outline-review/` 保留在仓库里没有删：它有自己的一次真实实测记录
（2026-08-28，4/4 未检出且全部人工复核为真阴性），那份数据不该随模板改动一起消失；
别的模板若确实需要一个独立的骨架槽位，它仍然可用。

搬过来的两条经验：

- **每条判据末尾都写明「引哪一句」。** 骨架那边发现有两类判据天然缺引文锚点
  （「缺了某字段」引不出缺的东西、「条数对不上」是个计数不是一句话），
  不指定就会稳定地被闸门丢弃。这里的 S1 与 S4 属于同一类，处理方式相同：
  S1 引「已经写了的那部分」，S4 引「本该承载它的那条目标」。
- **preamble 里点明还没有正文。** 结构审核跑在一个字正文都没有的时刻，
  不说清楚，模型会去找一段不存在的正文。

## 返修预算：`chapter.maxRevisionRounds: 3`

这个数在 `templates/zhihu-chapter/template.yaml` 的**容器类型**上，
因为轮次记在根槽位的 `revision_round` 里。

给 3 的理由是**结构返修便宜**：实测结构生成约 31k input tokens，
只有场景返修（一轮 4 次审核 + 1 次重写）的三分之一，而结构错了下游每一场都跟着错。

没给 5 的理由是**收敛性零数据**：场景那边实测是非单调的
（S2 连着三轮各报不同的句子）。3 轮最坏约 93k input，够看清它收不收敛；5 轮是 155k。
改成 5 是模板里的一行，退不回已经花掉的钱。

**这个数同样没有实测支撑。** 如果第一次真实跑里出现「第 3 版仍被检出且检出的是新问题」，
说明判据或指令有问题，该回来改的是判据不是这个数。
