# scene-review 判据的来源与实测可靠度（D-28 要求的记录）

> **为什么这份记录不在 `SKILL.md` 里。**
> `SKILL.md` 的每一个字节都会进模型上下文：frontmatter 之后、首个 `## S<n>` 之前的
> 全部内容进 preamble，而 preamble 由 `context-builder.ts` 的 `buildReviewSlotTexts`
> 注入 system prompt。把「S3/S4 实测召回 0/3」写进去，等于在审核时告诉模型
> 「这两条反正没用」。所以记录放在这里——同一个目录，人看得到，模型看不到。
>
> （注意：`skill-loader.ts` 的 `parseSections` 里那句「无主内容不参与注入」的注释
> 与实际行为不符：非 `S<n>` 的二级标题之后的正文会落回 preamble，因而**会**被注入。
> 这是既有实现，R4 未改动，仅记录。）

R0.5 与 R4 两轮探针里，S3 都是 **0/3**，从未响过。这一跑它响了一次：

换句话说：**探针测出的边界，可能测的是探针，不是模型。**

**但 n=1，不要据此改判据文本，也不要改 D-28 的定案。**
它证明的只有一件事：S3 并非永远测不出来。要把它变成可依赖的数字，需要的是

**每一层都测了，层与层之间那根线没测。**

### S2 的检出数不是单调下降的：3 → 4 → 3

这一条要看清楚再下结论。**三轮点名的句子完全不重复**——
第 1 轮点的是「他知道自己一坐进车里就会忍不住把凭证掏出来再看」，
第 2 轮点的是「假的。他知道。经不起细看。」，
第 3 轮点的是「像是多看一眼，自己就要反悔。」。

所以不是「写作 Agent 没改」。**它每轮都把被点名的句子改掉了，
但同一类问题在新写的文字里重新出现。**

我一开始猜第 2 轮多一条是因为「改写时写长了」。**查了，不成立**：
`context_json.revision.priorRounds` 里存着历稿，第 1 稿 1282 字符、第 2 稿 **1251** 字符，
反而更短。也就是说这不是扩写带出的新问题，而是**等量替换**——
把挨批的句子换成别的句子，换上来的仍然落在同一条判据的射程里。

这不是收敛曲线，是**在一条判据上原地打转**。D-26 的上限拦的正是这个：
没有它，这个槽位会一直返修下去。**「任务永不因审核卡死」在这里第一次被真实兑现。**

### S3 抓住了一个真正的跨场景身份混淆

写作 Agent 把两个不同的病人合并成了同一个人：主线之一是「没有家属陪同的老人」，
而转院家属争的是**他自己的父亲**。`scene_003` 却让他管那位无家属老人叫「他父亲」。

> 问题（节选）：scene_002 里他全程在为自己的父亲争取转院（"我爸就是低烧"
> "省医院我联系好了"），其父并非这位无家属老人……把三条线里的"老人"与
> "转院家属之父"两个不同病人混成了同一人。

**它逐字引了上一场的台词来论证。** 这类缺陷正是「只有看全文才发现得了」的典型形状，
而它在**槽位尺度**就被抓住了——因为审核 Agent 手上有结构概要 + `dependsOn` 注入的上游正文。

**这条数据直接影响「要不要做组装后全文审核」的判断**：出现了全文尺度的缺陷，
现有机制当场抓住并定点修复。这比「没观察到全文缺陷」（缺席证据）硬得多。

S4 那两次命中也带着同样的跨槽位推理——`scene_001` 那条明写
「下一场（scene_002）标注的起点是'小林等赵敏回应那一瞬'，而正文里这一瞬已被
赵敏的答复盖过，下一场将无法从设计好的局面接续」。

**S3 从 1/18 变成 5/28，不再是「在线但未验证有效」。** D-28 当初留着那个 0/3
就是为了有朝一日观察到这个变化。观察到了两次（v4-pro 换档那次、这次）。

### 新的失败形态：**跨判据震荡**（不是同一条判据原地打转）

首跑记的非单调是 S2→S2→S2，同一条判据在新句子上反复响。这次不一样：

| 槽位 | r0 | r1 | r2 | 终局 |
|---|---|---|---|---|
| `scene_003` | **S3** | **S2** | **S3** | 预算耗尽，按现状放行 |
| `scene_004` | **S3** | **S3 + S4** | **S2** | 预算耗尽，按现状放行 |

**修 S3 引出 S2，修 S2 又引出 S3。** `scene_003` r1 那条 S2 尤其说明问题：
为了修身份混淆去补交代，写作 Agent 写下「赵敏知道他那间房里存着不同的判断……
两样都没错，也都不会当着人点破」——**顺手把结构里明写「仍不点破」的东西点破了**。

**根源是返修粒度：为了改一句话，写作 Agent 重写了整场，于是每次都碰倒别的东西。**
这与结构返修「整棵树换掉」的风险是同一个形状。
**该动的是让返修只重写被点名的部分，不是把 `maxRevisionRounds` 往上调**——
调上去只是让它多震荡几轮。

  从裁决表上看像「S2 顽固不改」，实际是**每改一次就新犯一次**。

而 `d4fda471/scene_004` 的 4 条**全是原稿自带**——它的预算耗尽是审核召回问题
（S3、S4 在 r0 都漏了），与返修粒度无关。两种失效模式，不该混着说。

#### 一条不成立的推论，记下来免得以后自己骗自己

**附带改动率并不能预测哪次返修会造出新缺陷。**
42.2% 那次造出 0 条新缺陷，7.3% 那次造出 1 条。n=10，别当规律用。

成立的只有两句：返修**确实**在造缺陷（5/27），造出来的缺陷**确实**吃掉了预算
并导致带病发货（scene_003）。「把 diff 缩小就能少造缺陷」是**合理猜测，没验过**。

#### 这否决了最便宜的那个方案

提示词里**早就写着**这条约束（`context-builder.ts` 的返修段）：

> 请针对尚未解决的问题定点修改，未被指出问题的部分保持原样，然后提交完整正文。
> 注意：往轮已经改好的地方不要改回去。

写着，然后 72.8%。和 S3/S4 的强制对账实验是同一个教训：**把话说重救不回来。**
剩下的只有机械保证——提交后拿旧稿对账，未被点名的区段改了就打回。
（但先注意上一节：scene1_call 附带改了 12% 仍然一轮收敛，
「零附带改动」这个阈值大概率过严，阈值定在哪里是下一个要设计的东西，不是拍的。）

### 两个槽位带着已知缺陷发货

这是预算上限第二次在生产中生效，也是第一次**一次跑里两个槽位同时耗尽**。
两条未修的 finding 都经人工复核为**真阳性**：

- `scene_003`：药袋位置自相矛盾（开场在「桌角」，后文「怀里那只塑料袋滚出去」）。
- `scene_004`：「像是她整个后半夜攒着的疑问一次都涌到了喉口」是拍不到的心理解释。

任务列表的措辞经核对是对的（D-30）：
「5 个槽位已完成，**其中 2 个返修次数用尽、按现状放行**，产物已组装」——没有说「通过」。

### 引文闸门第一次有分母：**8 条 finding，0 条被丢弃**

「每条判据末尾写明引哪一句」这条设计，此前两次真跑都是 0 finding、分母也是 0。
这次 8 条 finding **全部**逐字核得上。

注意这验到的是**闸门不误杀**，不是「闸门能拦住编造的引文」——
后者仍然一次都没观察到（要观察到它，得有模型编引文，而它没编）。

### 41 次调用 vs 40 行裁决：`ASSIGNMENT_OUTPUT_INVALID` 复现

`scene_003` 的一次审核调用推理完了但没走 `complete_assignment`，
因此 `slot_reviews` 里不留任何行，系统重试后成功。

上一次记这条时写的是「任何按 `slot_reviews` 统计审核可靠度的口径都会漏掉它」。
**它第二次出现，说明不是偶发。** 上面那张「10 次」的表严格说是 10 次**裁决**，
真实调用是 10.25 次/条。**以后统计口径按 `executions` 算，不按 `slot_reviews`。**

### 一个被证伪的预测：接缝复述不是系统性缺陷

跑之前我预测过：结构里明写「接住上一场停点（X）」，写作 Agent 会把 X 再演一遍，
三道缝都会出现复述（依据是上一份产物 `2cdcbdc8` 的两道缝都是原样复述，
例如「四根手指还压在纸的边角上……」→「那四根手指还压在纸角上。」）。

**三道缝，一道都没复现那个形态：**

| 缝 | 形态 |
|---|---|
| 1 → 2 | **干净推进**。「小林把托盘往上端了端，仍没放」一句带过前态，赵敏随即给出回应（新事件） |
| 2 → 3 | **先重述再推进**。约一句半重新架起同一画面才动 |
| 3 → 4 | **轻锚点**。引上一场最后那句台词「人先救回来」作铰链，随即进抢救动作 |

所以「承接」有两种写法——确认后推进、原样复述——**而复述只在 `2cdcbdc8` 那一跑
稳定出现。n 在两个方向上都太小，不足以支撑「接缝审核」这个功能立项。**

## 什么时候才该跑 `run-r4-regression.mjs`

这个脚本一次 116 个真实调用、约 42 万 token（推理型号 65 万）。**它不是常规检查项，
不要放进 CI，不要「顺手跑一下看看」。** 只有这三种情况跑：

1. **改了 `skills/scene-review/SKILL.md` 的判据正文或 frontmatter**——判据变了，
   老数字就不再描述现在这套东西。
2. **准备换模型档位**（改 `config/providers.yaml` 的 `aliases`，或换供应商）。
3. **改了会进 system prompt 的注入路径**：`context-builder.ts` 的 `buildReviewSlotTexts`、
   `skill-loader.ts` 的 `parseSections`。这两处动了，模型看到的东西就变了。

**以下情况不用跑**：改 application/domain/api 代码、改数据模型、改前端、加测试、
重构、以及任何不改变「模型收到的字节」的改动。判据文本没动，这个数字就没动，
再跑一次只是花钱买同一个结论。

跑之前先确认 `--out` 指向新文件名：`probe/results-r4.json` 是 flash 档位的
**发布基线**，被覆盖就再也拿不回来（那 42 万 token 白花）。

> 2026-08-27 的教训：本次会话跑了三次，只有第一次（发布闸门）是必要的。
> 换档实验花掉 124 万 token、没有改变任何决定，其中 58.9 万因为没先确认
> v4-pro 是推理型号（`max_tokens` 沿用 flash 的 2000）而全部作废。
> **推理型号必配 `--max-tokens 8000`。**

## 换档实验：deepseek-v4-pro（2026-08-27）

Q-30「更强的模型档位」已测。同一份 SKILL.md、同一批 29 条用例、同一个端点、
同 temperature / 种子 / 并发，**只动模型**（`--model deepseek-v4-pro`）。
原始数据 `probe/results-r4-pro-8k.json`，116 次调用 / 653,123 token。

| | v4-flash（基线） | v4-pro |
|---|---|---|
| S1 召回 | 3/3 | 3/3 |
| S2 召回 | 3/3 | 3/3 |
| **S3 召回** | 0/3 | **2/3**（neg-16, neg-18） |
| **S4 召回** | 0/3 | **1/3**（neg-21） |
| **16 条正例场景级误报** | **0** | **9**（56%） |
| 对照 ctl-29（只倒置句序，不该被打回） | 未被打回 | **被打回** |
| token | 419,985 | 653,123 |

**S3/S4 的能力边界不是绝对的，它随档位移动——但这个召回是拿精度换来的，代价压倒收益。**

误报从 0/16 涨到 9/16。R0.5 结论第 3 条说得很清楚：
**误报 0 是这套东西能自动跑起来的前提**。9/16 意味着超过一半的干净场景会被打回返修，
预算烧在不存在的问题上——而返修预算只有 2 轮。

**引文校验救不了它**：61 条 finding 里 55 条引文逐字核得上，
9 条正例误报**全部**带着真引文活过 `verifyFindings`（D-11 的证据闸门）。
它们不是编的，是**实打实的判断分歧**——正因为讲得通，才没有任何机械规则能筛掉。

**一个我没有权限单方面裁定的问题**：这 9 条里至少有一部分看着像**真的**。
例如 pos-02，模型指出老周还没打开信封就说出了凭证上的具体金额。
这到底是模型过严，还是那 16 条正例的标注本身太宽？
n=16、且争议点都是判断题，我分不开。要分开只能由人逐条裁定这 9 条——
**在那之前，「误报 9/16」这个数应读作「模型与现有标注的分歧率」，不是「模型错了 9 次」。**

### 结论

**不切 v4-pro。** 门槛（S1/S2 召回 + 0 误报）是发布闸门，它挂在误报那一项上。
S3/S4 的 2/3 与 1/3 记录在案，作为「这两条判据并非永远测不出来」的证据——
D-28 当初留着它们、留着那个 0/3，为的就是有朝一日能观察到这个变化。**现在观察到了。**

### 顺带一条与实验成败无关、但影响产品的发现

**v4-pro 会真的回 `reasoning_content`**（flash 那 116 次的 `reasoning_tokens` 合计为 0，
pro 每次约 2000–7000）。`src/server/domain/revision-context.ts` 文件头写着
「`stripReasoning` 现有调用方喂进来的恒为 undefined，是纵深防御」——
**那句话只在 flash 档位上成立**。真要切到推理型号，那道网就从空转变成承重，
NFR-005 的端到端用例也才第一次有真实流量去踩。

### 这次实验踩到的坑（留给下一个人）

第一次跑 v4-pro 用的是脚本默认 `max_tokens: 2000`，116 次里 **49 次 PARSE_ERROR**，
raw 全是空字符串——`completion_tokens` 1998 **全部**是 `reasoning_tokens`，
思维链把输出预算吃光了，可见内容一个字没剩。
**那一跑测到的是 token 上限，不是能力**，数字全部作废（原始数据留在
`probe/results-r4-pro.json`，只作反面教材，不要引用它的召回数）。
推理型号必须配 `--max-tokens 8000`（实测最高用到 7248）。
抬上限对 flash 基线是空操作：它 116 次里最大才 543。
