# scene-review 判据的来源与实测可靠度（D-28 要求的记录）

> **为什么这份记录不在 `SKILL.md` 里。**
> `SKILL.md` 的每一个字节都会进模型上下文：frontmatter 之后、首个 `## S<n>` 之前的
> 全部内容进 preamble，而 preamble 由 `context-builder.ts` 的 `buildReviewSlotTexts`
> 注入 system prompt。把「S3/S4 实测召回 0/3」写进去，等于在审核时告诉模型
> 「这两条反正没用」。所以记录放在这里——同一个目录，人看得到，模型看不到。
>
> （注意：`skill-loader.ts` 的 `parseSections` 里那句「无主内容不参与注入」的注释
> 与实际行为不符：非 `S<n>` 的二级标题之后的正文会落回 preamble，因而**会**被注入。
> 这是既有实现，R4 未改动，仅记录。）

## 实测可靠度（R0.5 预研）

依据：`notes/R0.5-REVIEWER-PROBE-REPORT.md`、`notes/R0.5-ADDENDUM-PROMPT-ARCHITECTURE.md`。
29 条用例（16 正例 / 12 反例 / 1 对照），模型 `deepseek-chat`，三种提问架构下结论一致。

| 判据 | 召回 | 误报 | 状态 |
|---|---|---|---|
| S1 首段承接 | 3/3 | 0/16 | 已验证有效 |
| S2 可见行动 | 3/3 | 0/16 | 已验证有效 |
| S3 撞设定 | **0/3** | 0/16 | **在线但未验证有效** |
| S4 停点兑现 | **0/3** | 0/16 | **在线但未验证有效** |

S3 / S4 照样上线是 D-28 的定案：它们的误报为 0（不添乱），
而删掉就再也观察不到它们何时开始生效——那个 0/3 本身是一条可跟踪的基线。
回归脚本：`probe/run-r4-regression.mjs`（读的正是本目录的 `SKILL.md`）。

**已排除的救法**：把 S3/S4 写得更详细救不回来（附录 §2 的强制对账实验——
模型做了对账、把矛盾一字不差写进自己的工作区、然后照样放行）。
**不要为了把这个数字刷上去而改判据文本**：那既不成立，又会毁掉基线的可比性。

## 真实产品链路上的第一次端到端跑（2026-08-27）

在此之前，**产品的审核路径从未对着真实模型跑过**：R0.5 与 R4 的数字全部来自
`probe/` 下的独立探针脚本（自造用例、自己拼 prompt），产品这一侧只跑过 FakeProvider。
八个历史库里没有一个有 `revision_round` 列，就是这件事的证据。

这一跑补上了那个空白。`run-task.ts --provider real`、模板 `zhihu-chapter`、
`fixtures/chapter-packet.txt`、模型 `deepseek-chat`（= v4-flash）。
**33 次调用 / 460 秒 / 零失败**，产物 14126 字节。
结构 Agent 自己设计出三场并串好依赖（`scene_fuyue → scene_shipo → scene_tanpai`）。

| 判据 | 检出 | 调用次数 | 引文被丢弃 |
|---|---|---|---|
| S1 首段承接 | 0 | 6 | 0 |
| S2 可见行动 | **2** | 6 | 0 |
| S3 撞设定 | **1** | 6 | 0 |
| S4 停点兑现 | 0 | 6 | 0 |

三场分别返修 1 / 2 / 0 轮，**全部正常通过，没有一场走到预算耗尽**。
24 条 finding 的引文**全部**逐字核得上，D-11 的闸门一条都没丢弃。

### S3 第一次响，而且判对了 —— 这一条要单独记

R0.5 与 R4 两轮探针里，S3 都是 **0/3**，从未响过。这一跑它响了一次：

> 本场结尾让老周先行离场并留下「明儿个我在茶楼外头等你」的具体安排，林越独自
> 留在空了的雅间——这正对应章节骨架给场景三（scene_tanpai）预留的结束状态……
> 本场应停在『老周把凭证推回桌上』这个点，把『老周离场+明日之约+林越独留雅间』
> **交还给场景三承接**，否则提前消耗了下一场的设定。

它读了骨架，比对了尚未写作的下一场的规划，发现**第二场提前用掉了第三场的结尾**。
写作 Agent 按意见改掉了那一段，第 2 轮 S3 复审通过；第三场随后 S3 也判 no_finding
（结尾已经还回来了，不再冲突）。**检出 → 定点修 → 复审通过**，完整闭环。

**这说明 0/3 很可能是构造用例的产物，不是能力天花板。** R0.5 的 29 条用例里，
「撞设定」是在单条正文内部人工植入的矛盾；而真实任务里 S3 面对的是
**真实骨架 + 真实前后场依赖 + 尚未写作的下游规划**，信息结构完全不同。
换句话说：**探针测出的边界，可能测的是探针，不是模型。**

**但 n=1，不要据此改判据文本，也不要改 D-28 的定案。**
它证明的只有一件事：S3 并非永远测不出来。要把它变成可依赖的数字，需要的是
在真实链路上多跑几章，而不是再去调 SKILL.md 的措辞。

### 顺带暴露的产品缺陷（与审核无关，但这一跑才看得见）

`executions.input_tokens / output_tokens` **在生产中恒为 NULL**。
适配器发了 `stream_options: {include_usage: true}`、正确解析了 usage，
`agent-runtime` 也跨轮累加了，`assignment-runner` 也带出来了——
**然后 `production-engine` 把它丢在地上，没有任何一处写回 execution。**
`m4-measure`（121 条）与 `m7-accept10`（68 条）里 token 列同样全空，
说明这从 M4 起就坏着，**不是 R0–R4 引入的**。

测试没抓到的原因很典型：`m2-transaction-boundaries` 与 `m3-application-boundaries`
都**直接调** `markSucceeded` / 完成服务并传 usage，验的是那个接缝本身；
没有任何一条测试驱动引擎跑完一整轮、再断言 token 落库。
**每一层都测了，层与层之间那根线没测。**

## 什么时候才该跑 `run-r4-regression.mjs`

这个脚本一次 116 个真实调用、约 42 万 token（推理型号 65 万）。**它不是常规检查项，
不要放进 CI，不要「顺手跑一下看看」。** 只有这三种情况跑：

1. **改了 `skills/scene-review/SKILL.md` 的判据正文或 frontmatter**——判据变了，
   老数字就不再描述现在这套东西。
2. **准备换模型档位**（改 `config/providers.yaml` 的 `aliases`，或换供应商）。
3. **改了会进 system prompt 的注入路径**：`context-builder.ts` 的 `buildReviewSlotTexts`、
   `skill-loader.ts` 的 `parseSections`。这两处动了，模型看到的东西就变了。

**以下情况不用跑**：改 application/domain/api 代码、改数据模型、改前端、加测试、
重构、以及任何不改变「模型收到的字节」的改动。判据文本没动，这个数字就没动，
再跑一次只是花钱买同一个结论。

跑之前先确认 `--out` 指向新文件名：`probe/results-r4.json` 是 flash 档位的
**发布基线**，被覆盖就再也拿不回来（那 42 万 token 白花）。

> 2026-08-27 的教训：本次会话跑了三次，只有第一次（发布闸门）是必要的。
> 换档实验花掉 124 万 token、没有改变任何决定，其中 58.9 万因为没先确认
> v4-pro 是推理型号（`max_tokens` 沿用 flash 的 2000）而全部作废。
> **推理型号必配 `--max-tokens 8000`。**

## 换档实验：deepseek-v4-pro（2026-08-27）

Q-30「更强的模型档位」已测。同一份 SKILL.md、同一批 29 条用例、同一个端点、
同 temperature / 种子 / 并发，**只动模型**（`--model deepseek-v4-pro`）。
原始数据 `probe/results-r4-pro-8k.json`，116 次调用 / 653,123 token。

| | v4-flash（基线） | v4-pro |
|---|---|---|
| S1 召回 | 3/3 | 3/3 |
| S2 召回 | 3/3 | 3/3 |
| **S3 召回** | 0/3 | **2/3**（neg-16, neg-18） |
| **S4 召回** | 0/3 | **1/3**（neg-21） |
| **16 条正例场景级误报** | **0** | **9**（56%） |
| 对照 ctl-29（只倒置句序，不该被打回） | 未被打回 | **被打回** |
| token | 419,985 | 653,123 |

**S3/S4 的能力边界不是绝对的，它随档位移动——但这个召回是拿精度换来的，代价压倒收益。**

误报从 0/16 涨到 9/16。R0.5 结论第 3 条说得很清楚：
**误报 0 是这套东西能自动跑起来的前提**。9/16 意味着超过一半的干净场景会被打回返修，
预算烧在不存在的问题上——而返修预算只有 2 轮。

**引文校验救不了它**：61 条 finding 里 55 条引文逐字核得上，
9 条正例误报**全部**带着真引文活过 `verifyFindings`（D-11 的证据闸门）。
它们不是编的，是**实打实的判断分歧**——正因为讲得通，才没有任何机械规则能筛掉。

**一个我没有权限单方面裁定的问题**：这 9 条里至少有一部分看着像**真的**。
例如 pos-02，模型指出老周还没打开信封就说出了凭证上的具体金额。
这到底是模型过严，还是那 16 条正例的标注本身太宽？
n=16、且争议点都是判断题，我分不开。要分开只能由人逐条裁定这 9 条——
**在那之前，「误报 9/16」这个数应读作「模型与现有标注的分歧率」，不是「模型错了 9 次」。**

### 结论

**不切 v4-pro。** 门槛（S1/S2 召回 + 0 误报）是发布闸门，它挂在误报那一项上。
S3/S4 的 2/3 与 1/3 记录在案，作为「这两条判据并非永远测不出来」的证据——
D-28 当初留着它们、留着那个 0/3，为的就是有朝一日能观察到这个变化。**现在观察到了。**

### 顺带一条与实验成败无关、但影响产品的发现

**v4-pro 会真的回 `reasoning_content`**（flash 那 116 次的 `reasoning_tokens` 合计为 0，
pro 每次约 2000–7000）。`src/server/domain/revision-context.ts` 文件头写着
「`stripReasoning` 现有调用方喂进来的恒为 undefined，是纵深防御」——
**那句话只在 flash 档位上成立**。真要切到推理型号，那道网就从空转变成承重，
NFR-005 的端到端用例也才第一次有真实流量去踩。

### 这次实验踩到的坑（留给下一个人）

第一次跑 v4-pro 用的是脚本默认 `max_tokens: 2000`，116 次里 **49 次 PARSE_ERROR**，
raw 全是空字符串——`completion_tokens` 1998 **全部**是 `reasoning_tokens`，
思维链把输出预算吃光了，可见内容一个字没剩。
**那一跑测到的是 token 上限，不是能力**，数字全部作废（原始数据留在
`probe/results-r4-pro.json`，只作反面教材，不要引用它的召回数）。
推理型号必须配 `--max-tokens 8000`（实测最高用到 7248）。
抬上限对 flash 基线是空操作：它 116 次里最大才 543。
