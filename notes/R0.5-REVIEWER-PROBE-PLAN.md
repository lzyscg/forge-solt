## 1. 这件事要回答什么

`notes/AUTOMATED-REVIEW-REVISION-DESIGN-V0.1.md` 提出了 32 条决议（D-21～D-52）、

那整座建筑压在一个从未验证过的假设上：

> **DeepSeek 这一档的模型，能不能可靠判断「这段内容写得行不行」。**

设计自己承认它没被证明（§2.3、§17.4「FakeProvider 不能证明 Reviewer 能识别真实质量问题」），
却把验证排在**第八个阶段**。这与本项目自己的教训相反——Q-14：
`type: "object"` 少一行，M3 的 508 条测试全绿，因为 FakeProvider 不校验 schema；
方案 §12.2 正因如此把 M4（真实 Provider）排在 M6（UI）**之前**。

**R0.5 就是把那次验证提到最前面。** 1–2 天，不写一行产品代码。

### 结果如何影响决策

| 结果 | 对设计的影响 |
|---|---|
| 召回率高、误打回率低 | 闸门 B 成立，可以往下做；全局审核的价值被间接支持 |
| 召回率高但误打回率也高 | 返修预算（D-27/D-32）和终止性变成**第一优先**，不是配角 |
| 召回率低 | 审核 Skill 需要大改；32 条决议先别碰——先解决「审核员看不出问题」 |
| 各缺陷类型差异大 | 首版只保闸门 B 中**测得准**的那几类判据，其余延后 |

## 3. 用例设计

### 3.1 核心原则：缺陷用机械变换制造，不靠手写

**这是整个实验成不成立的关键。** 手写的缺陷会带上人的文风痕迹，
模型可能靠「这段不像模型写的」发现它，而不是靠判断质量——
那样测出来的召回率是假的。

`probe/build-cases.mjs` 已实现三类机械注入，**全部实测生效**：

| 类型 | 做法 | 验证结果 |
|---|---|---|
| **D1 承接断裂** | 把 scene_3 的开头换成**同一章 scene_1** 的开头 | ✅ 上一场结尾是「老周盯着桌上的信封」，注入后开头变成「林越站在公交站台檐下，雨从五点开始下」——无可辩驳的断裂，且是真实生成的文字，零文风痕迹 |
| **D3 事实矛盾** | 后半段把「凭证/信封」替换为「欠条/布包」 | ✅ 三例都确认前半段仍用原词，形成自相矛盾 |
| **D4 停错地方** | 删掉结尾 3 段 | ✅ 已加过滤：**只挑 instruction 里明写「停在哪里」的场景**，否则「停错了」只是主观判断。删后仍 >400 字，远超 `minChars: 300`，保证缺陷是语义的不是字数的 |

当前产出：**12 正例 + 9 反例（D1/D3/D4 各 3）**。

### 3.2 还要补的一类：D2 心理解释代替事件

这是 SKILL 的 S3 着墨最多的判据（唯一给了「差/好」对照例的），不该跳过。
但它**没法机械注入**——必须手写。

**做法**：挑 3 个场景，把其中一段具体动作改写成同等篇幅的内心解释，
保持同样的语域和句式节奏。

**必须在报告里声明这 3 例是人工撰写的**，并且——如果 D2 的召回率显著高于
D1/D3/D4，要**怀疑是文风泄漏而非真实识别**，用一条对照验证：
把同一段动作原样保留但打乱语序（制造一个「读着别扭但不违反判据」的样本），
看模型会不会也打回。会，就说明它在挑文风不是挑判据。

### 3.3 正例的一个诚实性问题（必须写进报告）

12 个正例是**通过了确定性校验的真实产物**，但**没有人判定过它们质量合格**。

所以「误打回率」的严格含义是：
> 对真实产线产物的打回率。

如果模型打回了某个正例，**它有可能是对的**。因此：
**每一个被打回的正例都要人工看一眼那条 finding 讲得对不对**，
分成「误报」与「其实说得有道理」两类分开计数。
只报一个总数会把这个歧义藏起来。

## 4. 执行步骤

```bash
# 0. 前置：确认 .env 里 DEEPSEEK_API_KEY 有值（别打印它）
#    密钥只从 .env 读，绝不写进任何脚本、用例或报告

# 1. 抽取底料（只读，已验证）
node probe/extract.mjs          # → probe/raw-slots.json

# 2. 构造用例（已验证）
node probe/build-cases.mjs      # → probe/cases.json（12 正 + 9 反）

# 3. 手写补入 3 条 D2 用例（见 §3.2）

# 4. 写审核 Skill：照抄 scene-writing 的四条判据（见 §2.3）

# 5. 跑（需新写 probe/run.mjs）

# 6. 出报告（需新写 probe/report.mjs）
```

### 4.1 `probe/run.mjs` 要点

- 直接 POST DeepSeek 的 `/chat/completions`，**不要走 `src/` 里的适配器**——
  那会把预研和产品代码耦合起来，而且适配器带一堆本次用不上的机制。
- **给 Reviewer 的输入**（这是闸门 B 的真实形态）：
  章节执行包 / 章节骨架 / **上一场景正文** / 本槽位 instruction / 待审正文 / 审核判据。
- **要求结构化输出**：`{verdict: "PASS"|"REVISE", findings: [{criterion, quote, problem}]}`。
  `quote` 必须逐字出自待审正文——这同时预演了 §3 里那条「用 `includes` 验证证据」
  的剃刀方案能不能立得住。
- **盲测**：`label` / `defectKind` / `defectNote` 三个字段**绝不进 prompt**。
  建议 run 之前先断言一次 prompt 里不含这三个词。
- 顺序打乱，别让正例反例扎堆。
- 每例记：verdict、findings、耗时、token 用量。**耗时和用量要留**——
  §1 表格里「成本」那一栏要用它算。

### 4.2 `probe/report.mjs` 要出的数

```text
应打回召回率     = 反例中判 REVISE 的比例（按缺陷类型分别报）
误打回率         = 正例中判 REVISE 的比例（并人工二分：误报 / 其实有理）
目标定位准确率   = 判 REVISE 且 finding 指向注入缺陷的比例  ← 比召回率更重要
证据有效率       = quote 确实逐字出现在待审正文里的比例
平均耗时 / token
```

> **「目标定位准确率」是最该看的一个数。**
> 一个把所有东西都打回的模型召回率 100%，但毫无用处。
> 只有**指对了地方**的打回才能驱动返修——D-24「审核意见必须可执行」就是这个意思。

## 5. 会让结果变成假绿的几种做法（重点）

按项目规矩 3.4「每条断言都要反证过」，先把失败模式列出来：

1. **只喂反例。** 那么「全部打回」的模型得 100% 召回。
   **正例必须占一半以上**，误打回率和召回率一起报，缺一个这份数据就没有意义。
2. **缺陷太显眼。** 如果注入的是「他很紧张。他很紧张。他很紧张。」，
   测的是模型认不认得复读机。D1/D3/D4 用机械变换正是为了避免这个。
3. **label 泄漏进 prompt。** 包括隐晦的泄漏：case 顺序、id 里的 `pos/neg`、
   甚至「请判断这段是否被修改过」这类问法。**问法必须是「按判据审核」，
   不是「找出被动过手脚的地方」**——后者是一道完全不同、且简单得多的题。
4. **把三个故事的数据合并成一个数。** 见 §2.1。
5. **重跑到好看为止。** 先定跑几轮、取哪一轮，再跑。
   模型有采样方差，挑最好的一轮等于自欺。建议每例跑 1 次，样本靠用例数而不是重复数。
6. **只报数字不留证据。** 每个判 REVISE 的样本，它的 finding 原文要存下来。
   §1 那张决策表要靠人读这些 finding 才判得了「说得对不对」。

  → 砍 D-30 与 §12.5 carry-over（Round 2/3/4 反复缠斗的那块）
- Evidence 用 `content.includes(quote)` 验，**不做坐标协议**
  → 砍 D-44 / D-52
- 静态可满足性证明改成运行时快速失败 → 砍 D-41 / D-45 大部
- 删 D-39（模型能力契约，单用户场景是在防自己）
- **保留**：D-21 裁判权、D-27/D-32 双预算与持久化（防不收敛）、
  D-40 关活动执行、D-42 Reviewer 不注册 `report_work`
