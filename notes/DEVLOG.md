## M0–M2：契约、纯函数、持久化

### 定下来的东西

**契约先行。** `src/shared/` 里的 Zod schema 是前后端唯一的形状约定，
后端用它做响应校验，前端用 `z.infer` 推类型。这一步做在最前面的收益在 M5 兑现了：
写 API 层时几乎没有「这个字段到底叫什么」的往返。

**错误码全表 + 完备的 HTTP 映射。** `ERROR_HTTP_STATUS` 声明成
`Record<ErrorCode, number>` 并逐条写满。早期草稿写的是「部分表 + 其余默认 500」，
那会让附录 A 规定 409 的 `SLOT_NOT_READY` 悄悄变成 500。
`Record` 的完备性检查把「新增错误码但忘了配状态码」变成**编译错误**，
而不是一个要等到线上才发现的 500。

**Domain 层零 IO、不读时钟。** 换来的是 100% 分支覆盖可以强制执行（vitest 配置里写死了），
以及 AC-013 的确定性。代价是「现在几点」要由上层注入——
`task-service` 因此多了一个 `now` 参数，值得。

**同步驱动是正确性前提，不是性能选择（D-15）。**
选 better-sqlite3 的全部理由是：只有同步驱动才能保证事务块内不存在 await 点，
从而物理上杜绝「stop 事务插进读-判-写窗口」。这条被写进了类型
（`NotPromise<T>` 让 `run(async ...)` 编译不过），而不是只写进 code review 清单。

**循环外键用 DEFERRABLE 解决，不用「放弃外键」解决（D-18）。**
`tasks.snapshot_id` 与 `task_snapshots.task_id` 互相引用。
关掉外键会让 D-10 的完整性地基消失**且不报任何错**，所以宁可用延迟外键。
配套的硬要求是 `PRAGMA foreign_keys = ON`——它默认是关的，
关着的时候延迟外键**静默失效**。M0 的测试里专门有一条守它。

### 后来被证明重要的一个小决定

`TemplateCatalog` 加载失败的模板收进 `failures` 而不是让 `reload()` 抛错。
理由当时写的是「一个坏模板不许让整个列表页空白」，但真正的另一半是
**坏模板必须显式可见**——静默消失的表现是「我明明建了模板，列表里没有」，
比报错难查得多。这个决定在 M5 一路影响到了 `GET /api/templates` 的返回体形状
（不是裸数组，带 `failures`）。

## M3：生产引擎闭环

这是「严格串行、不可跳过」的关键路径之一。产出是一个能 headless 跑通完整任务的系统。

### 几条硬决议

**D-10：Execution Token 校验压进 UPDATE 的 WHERE 子句。**
不是「先 SELECT 判断再 UPDATE」，而是把判据写进 SQL，用 `changes !== 1` 判成败。
两者的差别是原子性：前者中间有窗口，stop 可以插进来，
于是一次已被取消的执行的结果照样被写进库。

**D-11：提交闸门只在成功时关闭。** 早期写成「提交后一律关闭」，
结果是模型第一次提交被拒之后就再也提交不了了。

**D-20：提交被拒 ≠ 本次 Assignment 结束。** 被拒只写 trace，不结算 execution。
这条修之前，一个模型「先交了个错的、改好之后再交一个对的」的正常行为，
会被系统自己判成迟到结果（`EXECUTION_STALE`）——三次修正尝试变成三次失败的 attempt，
把重试配额烧光。修完之后三次提交发生在**一个** execution 里，配额一点没动。

**D-13：结构校验失败的反馈必须是三段式（rule / message / agentHint），且一次给全。**
短路返回第一条违规会让模型改一条、再撞一条、再改一条，每次都烧一轮。

**D-19：失败原因的成文责任在 lifecycle / application 层，不在派生层。**
只有 lifecycle 手上同时有 execution、超时配置和违规列表；
让派生层去反推，就得把这三样都塞进签名，而它们对附录 B 其余 11 行毫无用处。
配套要求：写进 `error_message` 的必须是**一句可直接展示的完整中文**，不是错误码。

**附录 B 必须有兜底行（第 14 行）。** `TaskStatus × TaskPhase` 有 20 种组合，
表里只覆盖了一部分，`running` + `phase=done` 就落空。
派生函数跑在每次列表渲染上，**一条脏数据不该把整页打成 500**——
兜底返回一个诚实的「状态未知」，同时把组合原样写进 detail 便于排查。

### 一处对文档的修订

§9.2 原本把 DTO 投影层画在 `api/dto/`，实现放到了 `application/task-service.ts`。
两条理由：投影要跨五张表取数还要解冻结快照，是编排不是搬运，放进 api 层等于让
HTTP 层直接持有六个仓储；而且 CLI 也要它，CLI 不该经过 api 层。
§9.2 的实质约束（「`derive*Presentation` 只有一个调用点」）原样保留，只是地点改了。
**文档已相应修订。**

## M4：真实 Provider 与 Skill 调优

### 第一次真实调用就 400 了

`complete_assignment` 的入参是一个 Zod 判别联合，投影成 JSON Schema 时只写了 `anyOf`，
漏了根级的 `type: "object"`。DeepSeek 直接 400（`got 'type: null'`）。

值得记的不是这个 bug，是**它为什么在 M3 全绿的情况下依然存在**：
FakeProvider 不校验 schema。所以修完之后加的回归断言不是针对这一个工具，而是遍历全部：

```ts
it('每个工具的根 schema 都是 type:"object"（Provider 的硬要求）', () => {
  for (const [name, schema] of Object.entries(ToolSchemas)) {
    expect(toJsonSchema(schema)['type'], `工具 ${name} 的根 type`).toBe('object');
  }
});
```

按流程先改了文档 §3.4，再改的代码。

### 量化闸门：20 次实测

写了 `cli/measure-runs.ts` 作为 M4 的硬闸门。结果：

- 结构提案**首次通过率 20/20 = 100%**（目标 ≥80%）
- 两批共 25 次真实运行、157 个 assignment，**零 `validation_failed`**
- D-17 的头号风险没有发生，L1 缓解就够了，L2/L3/L4 一次没动

### 三件从数据里发现、而不是从测试里发现的事

**1. 报告本身藏了一个真失败。** 121 条 execution 对 120 个 assignment——
多出来的那一条是某个槽位模型只说话没调 `complete_assignment`。
第一版报告的口径把它算成了成功。加了 `slotsWithNoSubmissionAttempt` 指标。
这是我自己交付物里的缺陷，记在这里。

**2. 我自己的过度归因。** 报告初稿写「Skill 重写导致场景数收敛」，
但改动之前只有 n=1，那句话根本立不住。重写成两段：
**干净归因**（标题 `dependsOn` 骨架：0 → 20/20，改动前后可比）与**仅作观察**（场景数分布）。

**3. Token 统计结构性不可能。** 0/121 行有 usage。链路一处不缺，
但时序上填不上：提交发生在**工具调用内部**（这一轮 turn 还没结束），
而 `usage` 是 Provider 在**流的最后**才给的。
**刻意没修**——唯一干净的修法紧挨着 D-10 的条件 UPDATE，
那是全系统最不该在里程碑收尾时匆忙改动的一段 SQL。记成 Q-18。

### 一个不会让任何测试变红的 bug

`resolveDatabasePath(':memory:')` 把哨兵 `path.resolve` 成了 `<repo>/:memory:` 这个**真实文件**。
于是每一个声称「用内存库」的测试其实都在往仓库根目录写同一个文件，彼此看得见对方的数据。

更麻烦的是下游那句 `dbPath.includes(':memory:')` 对解析后的绝对路径**依然为真**，
所以「跳过建目录」的分支照常命中——代码看起来完全正确。

**测试全绿，只是失去了隔离**，而隔离的丧失要等到两条用例真的撞在一起时,
才会以「莫名其妙的偶发失败」的形式浮现。发现它靠的是 `git status` 里多出来一个 18MB 的文件。

回归用例因此断言的是**文件系统的可观察结果**，不是函数返回值——
只断言返回值的话，将来有人在下游重新引入一次 resolve，那条依然绿。

### 一个「看起来生效、实际什么都没做」的缓解手段

D-17 的 L3 是「换 `deepseek-reasoner`」。实测发现 `deepseek-reasoner` 与 `deepseek-chat`
**都解析到同一个 `deepseek-v4-flash`**，而且**不会有任何报错**。
按字面执行 L3 会换来同一个模型、通过率一点不变，
却让人误判「L3 试过了，该上 L4 了」——而 L4 是文档明确说「设计上的让步」的那一级。
L3 的目标模型已改为 `deepseek-v4-pro`。记成 Q-17。

## M5：API 与 SSE

产出 §9.1 全部 22 个端点 + SSE Hub + 错误映射。测试从 573 涨到 669。

### 分四块做

- **M5-A** Fastify 骨架 + 错误映射（`ForgeError → HTTP` 的唯一转换点）
- **M5-B** 模板与任务只读端点
- **M5-C** 写端点 + Provider 端点
- **M5-D** SSE Hub

### M5-A：错误映射的三条硬要求

1. 状态码全表来自 `shared/errors.ts`，**这里一个 if 都不写**
2. **内部错误码不得出网（D-18）**，但处理方式必须同时满足两面：
   **对外安全**（500 + 通用文案）、**对内刺眼**（error 级别 + 可 grep 的固定字样）。
   默默按原码返回是泄露，默默改写是掩盖，两个都不行
3. 非 `ForgeError` 一律通用文案，原始错误连同 stack 只进 pino——
   sqlite 的报错带表名和 SQL，Node 的报错带绝对路径

### M5-B：几个投影决定

**`GET /api/templates` 返回 `TemplateListResponse` 而不是裸数组。**
带上 `failures`，否则 `TemplateCatalog` 刻意收集坏模板这件事到 HTTP 边界就没了——
列表页确实不空白了，但用户再无从知道自己那个模板为什么不在里面。**先改的文档。**

**`failures` 只出 `dirName`，不出 `sourcePath`。** 绝对路径不出网。
（这条后来发现做得不彻底，见下面的审查部分。）

**查询参数解析不出来一律 400，不静默兜底。**
`?after=abc` 退回 0 会**从头重放整条轨迹**，而调用方拿到的是一个格式完全正确的 200——
它没有任何办法知道自己传错了。附录 A 的 `TASK_INPUT_INVALID` 触发条件相应扩充为
「必填输入缺失，**或请求参数非法**」。不新增错误码：对调用方而言
「你传的东西不对，改了再来」是同一件事。

**发现并修掉一个排序不确定性。** `updated_at` 只到毫秒，连着建两个任务可能并列，
而并列行的先后由 SQLite 的查询计划决定——今天是 rowid 序，
换成走索引就可能是另一个序。表现是任务列表在两次刷新之间自己跳行，**而数据一个字没变**。
加了 `id DESC` 破平：ID 是 randomUUID，这个次序本身没有意义，有意义的是它**稳定**。

### M5-C：HTTP 把一个隐含前提拿掉了

**`lifecycle.dispatch()`：同步校验 + 后台推进。**
`start/resume/retry` 返回的 Promise 在**整轮生产结束**时才 resolve（几分钟），
所以路由不能 await；可一旦不 await，同步抛出的校验错误（「任务不是 ready，不能 start」）
就变成了一条无人接手的 rejection，而请求返回 200。
拆成两段：迁移与校验同步（失败同步抛，交给 setErrorHandler），推进留后台。

**引擎的 pump 会被一个异常永久毒死。**
`pump = pump.then(runPump)` 一旦 rejected，之后每次 enqueue 挂上去的 `then` 都不执行——
**进程活着，但再也跑不动任何任务**，且只在控制台留一条 unhandled rejection。

这个 catch 在 M5 之前不存在，因为在此之前**总有人在 await**：
CLI 和集成测试都 `await lifecycle.start(id)`，`tick` 抛出的东西会直接变成那次调用的失败。
HTTP 把这个前提拿掉了。加了 `settleEscapedError`：把任务落到终态、写 trace、
整段再包一层 try/catch（收尾自己再抛就前功尽弃）。

**`reasonOf` 的信息泄露。** 原实现「是 Error 就用它的 message」，
而 `task.error_message` 那一列**既进 API 响应也直接显示给用户**。
一个裸 Error 的 message 可能来自 sqlite（带表名和 SQL）、Node 的 fs（带绝对路径）或 fetch（带 URL）。
这与 §9.3 是同一条纪律，只是那条守 HTTP 边界，这条守**数据库里那一列**——
写进去就晚了，后面每一次读都在泄露。它同时也违反 D-19：
一句英文的 `no such table` 不是「可直接展示的完整中文」。

**`recoverOnStartup` 此前没有生产调用点。** §8.6 要求它在 HTTP 开始监听**之前**跑完，
而 M5 是第一个有「监听」这件事的里程碑。补进了 `main.ts`。

### M5-D：SSE 的几个设计取舍

**`state` 事件由 Hub 观测 trace 得出，没有 `publishState` 这个方法。**
Hub 在每条 trace 推送之后读一次权威状态，与上次推过的三元组比对，**变了才推**。
反过来做（在 lifecycle / engine 的每个状态迁移处补一行）要改十几个调用点，
漏掉任何一个的表现是「界面卡在旧状态，刷新一下才对」——
最难被测试抓住、也最容易被当成偶发的一类 bug。
观测式的数据源就是数据库，不可能与真实状态漂移。
代价是它依赖一条隐含约定：**改状态的地方必须写 trace**（记成 Q-22）。

**先注册订阅者，再读历史补发，中间不得有 await。**
顺序反过来会留下一个窗口：在「读完历史」与「注册」之间提交的 trace
既不在补发里、也不在实时流里，永久丢失。
这条时序成立**依赖 better-sqlite3 的同步读**——将来换异步驱动必须改写。

**`Last-Event-ID` 优先于 `?after=`。** 浏览器 `EventSource` 重连时会原样重发同一个 URL
（连同当初那个 `after`），同时带上 `Last-Event-ID`。让 query 赢的话，
断线越多重复越多。

**测试分两层。** Hub 层用假客户端（能同步断言，不必与网络赛跑）；
HTTP 层用**真监听 + 真 fetch**——`app.inject()` 会等响应结束，而 SSE 的响应永远不结束。

顺带查出一件事：真 HTTP 测试的 `afterEach` 每次白等约 4 秒，
因为 `server.close()` 在等 undici 的 keep-alive socket 超时。
给测试开 `forceCloseConnections`，那个文件从 4.4 秒降到 0.4 秒。
生产不开——强制断开会打断真正在途的请求。

### 真实端到端

真服务 + 真 DeepSeek 跑通一整章：5/5 槽位、13,648 字节产物、
154 条 trace（id 严格单调递增）、2566 条 delta、14 条 state、6 次心跳。
全库六张表逐列扫 API Key 与 `reasoning_content`：**0 命中**。

**这次实测发现了一个测试发现不了的问题**：
`assignment_created/started/submitted` 各 6 条，而 `assignment_completed` 只有 5 条。
结构那条路径**只在失败时收尾**（`failAttempt` 写 `assignment_failed`），
成功时写完 `validation_passed` 就没有下文了。

后果有两层。轻的一层是时间线：结构那一格永远处在「已提交、已校验、然后没有下文」，
看起来像卡住了。重的一层是任何按 trace 统计「跑完了几次 assignment」的东西
（`measure-runs.ts` 就是）都会**系统性地、每次一样地**少算一次，
因此不会被当成异常。

这与 M4 修掉的「`assignment_started` 写两次」是同一类问题：
**一条 assignment 的轨迹必须自洽，缺一半和多一半同样坏。**
修完之后重跑实测：6/6/6/6，与 6 条 execution 对齐。

### 收尾的独立审查

M5 由主 Agent 独立完成（subagent 环境当时不可用），收尾时开了一轮**不带上下文的审查**。
报了 7 条应修 + 5 条建议，**全部属实，没有一条是凑数的**。挑两条最有价值的：

**1. stop 之后紧接着 resume，任务永久卡在 `running`。**
`enqueue` 里那句「正在跑的就别重复入队」在 tick 收尾窗口里把 resume 静默丢弃了：
状态已经被同步改成 running、trace 也写了，却没有任何东西会再推它。
审查者**复现了它**，并且指出我原来那条 HTTP 版用例为什么是假绿的——
两次 inject 之间那个 await 恰好够 tick 收尾，窗口就错过了。
新用例把 stop 与 resume 压在**同一个同步块**里才守得住。

修法：去重判据只看队列、不看「是不是正在跑」，多排的那一轮由 `tick` 开头
「`status !== 'running'` 就返回」兜住——那一行本来就是为这种情况写的。
配套还得把 settler 在**开跑之前**摘下来，否则第二轮的等待者会被第一轮的结束顺手 resolve。

**2. 我那条「绝对路径不出网」的断言是恒为真的。**
唯一的坏模板样本失败在**编译期**（`status` 取值非法），报错里本来就没有路径；
真正会把 `sourcePath` 拼进 message 的是「读文件失败」那条分支，**没有任何样本覆盖它**。
断言写对了，样本没覆盖到它想守的那一类错误。
补了一个不含 `template.yaml` 的 fixture 目录之后，那条断言才真的能变红。

其余五条：SSE 首连全量重放（前端会把每条事件显示两次）、
新订阅者的 state 基线被广播给所有老连接（重拉风暴）、
`close()` 之后还能订阅（优雅关闭挂到超时）、
probe 完全没有超时**而且我的注释把原因说反了**、
内部错误码经 DTO 投影绕过 D-18 拦截（`message: "USER_STOP"` 会原样上屏）。

最后一条引出一次文档修订：附录 A 的「不直接返回给用户」，
准确范围是「**不得作为 HTTP 错误响应体的 `code`**」，
不禁止这些码出现在 `ExecutionView.error` 这类**投影字段**里——
那是对一次已发生的执行的诊断记录，把 `EXECUTION_CANCELLED` 换成 `STORAGE_ERROR` 反而是撒谎。
真正的要求是 D-19：写进去的时候就得是一句人话。

12 条全部修完，每条都配了**反证过**的回归测试——
逐条把产品代码改坏确认测试变红，其中有一条第一版写法改坏了也不红，重写了一版才守住。

### 复查找到的两个 bug

**1. 工作台的本地状态跨任务泄漏。**
TanStack Router 默认不因 params 变化重挂组件（`Match` 的 key 只在
`remountDeps` 有返回值时才变），而 `/tasks/$taskId` 没声明它。
于是从 `/tasks/A` 直接走到 `/tasks/B` 会复用同一个组件实例。

最狠的一处是时间线：trace 的 `sequence` 是**每任务从 1 开始**的
（`UNIQUE (task_id, sequence)`），而合并时按 sequence 去重。
实测里第一章有 34 条（seq 1..34）、第二章有 11 条（seq 1..11）——
B 的 11 条会被 A 留下的编号整段判成「已经有了」丢掉。
不报错、不白屏，只是时间线是错的。

同样被带过去的还有 `selectedSlotId`（槽位 id 来自模板，同模板的两个任务必然重名）、
`followLive`（停在 false，自动跟随静默失效）和 `commandError`（A 的失败提示挂到 B 头上）。

修在路由上加一句 `remountDeps`，而不是在三个组件里逐个 reset：
后者要维护一张「换任务要清哪些」的清单，漏一个的表现同样是静默的错数据。

**诚实说一句它现在有多难触发**：当前 UI 里没有任何一条从工作台直接跳到
另一个工作台的路径（唯一的出口是回列表，回列表会卸载）。要触发得靠
浏览器历史跳两格。但它会在**任何人加一个「下一个任务」链接的那一刻**变成日常路径，
而那时的现象是「时间线偶尔不对」——最难查的那类。

**2. 「有 N 条新事件」的 N 是编的。**
`useEffect(() => { if (!following) setPending(p => p + 1) }, [traces.length, following])`
把 `following` 也放进了依赖里，且无条件 +1。两个后果：
用户一往上滚，effect 重跑，立刻冒出「有 1 条新事件」——**没有任何新事件到达**；
以及一次推来三条也只 +1，点「回到最新」时以为只错过一条。
改成用 ref 记住上次的总量算差值，差值为 0 不动。

这条比第一条更值得记，因为它是**唯一一个用户看得见的具体数字**。
数字错了不会报错，只会让人不信任这个界面。

### 顺带补上的测试基础设施

复查前，`src/client/` 只有一个测试文件（`panel-subject.test.tsx`，10 条）。
`useWorkbench`、`TraceTimeline`、路由——一条都没有。第一个 bug 没被发现，
原因就在这里：它不在任何一条被断言过的路径上。

补了两个文件（路由级换任务、时间线计数），并发现了一个所有前端测试共有的隐患：
本仓库没开 `globals: true`，而 @testing-library 的自动清理挂在全局 `afterEach` 上，
**不开就不生效**。原来那 10 条恰好因为断言文案互不相同才没炸——
第二条用例只要与第一条共用一个词就会「找到多个元素」。两个文件都补了显式 `cleanup`。

同一类疏漏还有 `eslint.config.js` 里测试豁免的 glob 只写了 `.ts` 没写 `.tsx`，
而 vitest 的 include 是收 `.test.tsx` 的。眼下没触发，下一个 `.tsx` 测试里
写个 `any` 就会莫名报错。一并补上。

### 复查没有改、留给业务方定的

Q-25（已完成槽位看不到技术详情，UX §13.5 覆盖缺口）——

## 贯穿全程的几条经验

**1. 「测试全绿」不是判据，「改坏了会失败」才是。**
这个项目抓到的假绿：`Content-Length` 断言其实在测 Fastify（我写的 header 是死代码）、
「绝对路径不出网」恒为真、「resume 等自己那一轮」第一版守不住、
`:memory:` 共享磁盘文件从来没让任何测试变红。
养成习惯：写完断言就把产品代码改坏跑一遍。

**2. 最贵的 bug 是「系统性的、每次都一样的」那种。**
`assignment_completed` 少一条、token 恒为 NULL、`:memory:` 失去隔离——
它们都不是偶发，正因为每次都一样，所以看起来像正常行为。
偶发 bug 会被注意到，稳定的错误不会。

**3. 真实运行能发现测试发现不了的东西。**
HTTP 400、`assignment_completed` 缺失、token 恒 NULL、L3 是个 no-op——
全部来自实跑，不是来自测试。替身不校验的东西，测试就守不住。

**4. 收尾时的独立审查视角比开发期更值钱。**
开发期的 subagent 主要省时间；收尾期的审查者能看见主 Agent
**结构上不可能看见**的东西——尤其是「我以为我测了」的那些地方。

**5. 先改文档再改代码，执行了十几次，一次都不后悔。**
它强迫你把「原文是什么 / 为什么改 / 不改的代价」写清楚，
而写不清楚往往就说明这个改动还没想明白。
`notes/OPEN-QUESTIONS.md` 里 23 条的一半是这个习惯的副产品。

**6. 「看起来生效、实际什么都没做」比「明显坏掉」更危险。**
D-17 的 L3（换个别名解析到同一个模型，无任何报错）、
`includes(':memory:')` 对误解析的路径依然为真、
我手写的 `Content-Length` 被 Fastify 覆盖——
三者都是「代码在那儿、看着对、跑起来没报错、但一点作用没有」。
判断方式只有一个：**去掉它，看有没有区别。**
