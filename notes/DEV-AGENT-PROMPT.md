## 工作纪律（违反其中任何一条，这次改动就是坏的）

**1. 每条断言必须先看着它失败。**
写完一个 `expect`，去把产品代码改坏，确认它变红，再改回来。
没红过的断言是装饰品。实施文档里标了「**必须反证**」的地方，
是最容易写成装饰的地方，交付时要逐条报告你看到它红了。

**2. 不要顺手重构。**
仓库里有已知的三处枚举重复（Zod / SQL CHECK / domain 表）。
**本次不消除它。** 重构混进来会让这次的 diff 没法审。

**3. 不要改需求文档。**
REQ、术语表、技术方案、UI Spec 都已经改到位了。
实现跟文档冲突时停下来报告，不要改文档迁就实现。

**4. 不要扩大范围。**
只做本阶段。看到下个阶段的东西「顺手也能做」——不要做。
看到不相关的 bug——记下来告诉我，不要修。

**5. 分层是 ESLint 强制的。**
`shared ← domain（纯函数，零 IO）← application ← runtime/infrastructure ← api`。
`src/server/domain/**` 强制 100% 分支/函数/行/语句覆盖。
往 domain 里放任何 IO 都会被 lint 拦下。

## 完成的定义

实施文档 §9 写了每个阶段的完成判据。除此之外，这四条命令必须真的跑过且全绿：

```bash
npm run typecheck
npm run lint
npm run test
npm run test:coverage
```

**R0 阶段特别注意：不该让任何现有断言变红。**
红了说明你的改动语义超出了预期——停下来查，不要改测试去迁就。

## 交付时报告这些

1. 四条命令的**实际输出**（粘贴，不要只说「通过了」）；
2. 每条「必须反证」的断言：你把什么改坏了、看到哪条红了；
3. 你偏离实施文档的地方，以及为什么；
4. 你发现但没修的问题。

## 不要做的事

- 不要 commit（我来）；
- 不要碰 `data/*.sqlite`——那几个库**没有备份**，`m4-*` 和 `m7-*` 是所有实测数据的唯一副本，只读；
- 不要碰 `probe/` 下的既有脚本和结果——它们是 R4 回归的基线；
- 不要在任何文件里写入 API Key 或密钥值（`.env` 存值且已被 git 忽略；`config/providers.yaml` 只放环境变量**名**）。

## 关于这个功能，有一件事你必须理解对

审核 Agent 只有**两条判据实测有效**，另两条在三种提问架构下都是 0/3。
四条**全部上线**——测不出来的照样实现，因为它们误报为 0（不添乱），
且删掉就再也观察不到它们何时开始生效。

**不要因为判据三/四测不出来就跳过它们，也不要试图去「优化」它们。**

由此还有一条**正确性要求**（不是文案偏好）：
系统任何输出——trace kind、API 字段、UI 文案、错误消息、代码注释——
**不得出现「审核通过」「质量合格」「已校验」**。统一用「未检出问题」。

理由：这个探测器只会漏、几乎不会冤，说「通过」是不实陈述。
项目有一条规矩是「错误消息不能撒谎」，这里是它的延伸。
