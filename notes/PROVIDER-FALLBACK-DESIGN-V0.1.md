# Provider 降级链设计 V0.1（D-66…D-70）

2026-08-31。起因：现在有三家可用 Provider，两家订阅制（额度会用完）、
一家按量付费（不会用完但花钱）。需要一个「高优先级的用完了自动往下走」的机制。

D-17 定的是 **模型** 升级阶梯（L1–L4：改提示词 → 降结构复杂度 → 换更强模型 →
文本 JSON 兜底），针对的是「结构 tool call 不稳」。**它没有 Provider 降级链**，
所以本文是新决策，不是对 D-17 的补正。

---

## §1 优先级链

业务方指定的顺序：

| 档 | Provider | 模型 | 性质 |
|---|---|---|---|
| 1 | `volcengine-ark-coding` | `deepseek-v4-flash` | 订阅，额度会用完 |
| 2 | `compshare-coding` | `deepseek-v4-flash-0731` | 订阅，**按调用次数**扣，一章约 429 次 |
| 3 | `deepseek` | `deepseek-chat` | **按量付费，永不耗尽，但真花钱** |

第 3 档永不耗尽这一点，使它成为链的正确终点：降级链必须有个不会失败的底，
否则「自动降级」在最坏情况下仍然是「任务失败」，等于没做。

**这三档不是同一个模型。** 第 1 档与官方的 `deepseek-chat` 是同一个模型
（官方 `deepseek-chat` 解析到 `deepseek-v4-flash`，已实测），
但第 2 档是**带日期的固定快照 `-0731`**，是另一个版本。
因此跨档的产物**不能直接比对**，这是 §4 那条决策的直接理由。

## D-66 别名是链，不是单点

`providers.yaml` 的 alias 从 `{provider, model}` 改为**有序数组**，
数组顺序即优先级。单对象写法继续接受，视为长度 1 的链（向后兼容）。

**为什么落在别名这一层**：`providers.yaml` 开头就写着「别名是快照冻结的单位……
别名 → 具体 provider/model 的解析发生在执行时（late-bound）」。
降级正是一次晚绑定解析，天然属于这里。模板、快照、历史任务**一个字都不用改**。

加载期校验每一档：provider 存在、model 在该 provider 的 `models` 列表里。
链上任何一档写错都在**启动时**炸，不留到运行期——这与既有的
「别名指向不存在的 provider 当场报错」是同一条理由。

## D-67 在任务边界定住，中途绝不换

任务创建时沿链选出第一个可用档，**写进 `tasks.pinned_providers_json`**，
此后该任务的每一次 `resolve()` 都读这个 pin，不再看链、不再看健康状态。

若任务跑到一半这一档的额度用完了：**该任务失败**，不切换。
下一次跑（新任务）才会选到下一档。

**为什么不中途切换。** 中途切换意味着一章的前半段和后半段由不同模型写成
（见 §1，第 2 档是另一个版本的模型）。而下一阶段的全部工作是 Skill 迭代——
**它干的事恰恰是比对产物**。一份「混血」产物混进对照组，得出的结论是错的，
而且错得很难发现：`executions.provider` 虽然记着，但任何忘了按 provider
分组的分析都会静默把它们并在一起。

代价是明确的：中途耗尽会浪费已完成的半章。**这是自愿付的代价，不是疏漏。**

**为什么要落库，而不是「反正任务失败了所以不会换」。**
不落库时「中途不换」只是一个**涌现属性**——它成立仅因为耗尽会让任务失败。
一旦并发跑第二个任务、或哪天改了失败语义，它会静默失效。
落库把它变成**构造性保证**：pin 存在，就没有第二条路径可走。
这与 R6 的思路一致（不提交的段落在机制上改不了，而不是「模型一般不会改」）。

## D-68 耗尽判定分两层，且第二层现在是空的

### L1 —— 与 Provider 无关，现在就能用

一次 Execution 在**重试与限流退避配额都用尽之后**仍以 Provider 级错误告终
（`PROVIDER_RATE_LIMITED` / `PROVIDER_ERROR` / `PROVIDER_UNAVAILABLE`），
即判定该 Provider 耗尽，标记之，并让任务失败。

它不需要知道任何一家的错误长什么样，因此**必然可用**。
代价是慢：要先把退避配额（最多 5 次、上限 1 分钟）走完才认输。

### L2 —— 每家的耗尽特征，跳过无谓退避

一张 `exhaustionSignatures` 表：命中 HTTP 状态 + body 模式即**立刻**判耗尽，
不走退避。

**这张表现在是空的，这是刻意的，不是没写完。**

我不知道火山方舟和优云智算在额度耗尽时返回什么。这件事**无法在不真烧掉一份
额度的前提下测出来**。凭猜写进去比空着更糟：一个猜错的特征会把正常的限流
误判成耗尽，于是好端端的 Provider 被拉黑，任务莫名其妙掉到付费档去烧钱——
而且因为它「看起来工作了」，没人会去查。

**填表的正确时机是第一次真的撞上。** 撞上时 L1 会兜住（任务失败 + 标记耗尽），
`executions.error_message` 里留着上游的原文，照着它把特征补进表即可。
届时请**同时把原文抄进本节**，让后人知道这个特征是从哪来的。

已知的一个参照：OpenCode Zen 余额不足时回 `401` + body 含 `CreditsError`
（`providers.yaml` 注释里记着，接入当日实测）。**但这不能推广到另外两家。**

### 冷却

订阅额度按月重置，而我们无从得知重置时刻。因此耗尽标记带**冷却时间**
（默认 6 小时），过期后下一个新任务会重新从链顶试一次。
代价是每 6 小时浪费一次调用，可忽略；收益是额度恢复后能自动爬回高优先级档。

## D-69 落到付费档必须响

链上可标 `paid: true`。选中这一档时写一条**醒目**的轨迹事件，任务上可见。

理由：第 3 档永不耗尽，意味着一旦滑下去，系统会**无限期、无提示地**持续花钱，
而表面上一切正常。这正是最该有信号的一类状态。

措辞受 D-30 约束——不许含糊成「已切换 Provider」，要写明**这一档是按量付费的**。

## D-70 降级决策本身进轨迹

不只记「用了谁」（`executions.provider` 已经在记），还要记**跳过了谁、为什么**。
只记结果的话，「为什么这次跑得比上次贵」在事后是查不出来的。

## §5 诚实声明

| 结论 | 依据 |
|---|---|
| 三家的 baseUrl / 模型 / tool call 可用性 | **实测**，`probe/provider-onboarding.ts`，各 n=2 |
| 一章约 143 次工具调用 | **实测**，R6 真跑（48 次执行 / 143 次工具调用），n=1 |
| 优云的倍率与额度换算 | 控制台原文 + 上面那个 143 的推算，**未实跑验证** |
| 第 1 档与官方是同一个模型 | **实测**（官方 `deepseek-chat` 响应 model 字段回 `deepseek-v4-flash`） |
| 火山/优云耗尽时返回什么 | **完全未知**。见 D-68 L2 |
| L1 能兜住耗尽 | **推断，未经真实耗尽验证**。它不依赖错误形状，因此推断的把握较大，但没跑过就是没跑过 |
| 6 小时冷却是否合适 | **拍的**。没有数据支持，改它不需要理由 |

**整个机制至今没有在一次真实的额度耗尽中被触发过。** 它是照着
「耗尽会以某种 Provider 级错误出现」这个假设建的。这个假设本身很稳，
但从假设到实证之间的距离，必须写在这里而不是被略过。
