**模型**：`deepseek-chat` 别名（服务端实际解析到 `deepseek-v4-flash`）

## 1. 结果

### 1.1 主批次 — `chapter-packet.txt`，连续 20 次

| 指标 | 目标 | 实测 | |
|---|---|---|---|
| 结构提案首次通过率 | **≥ 80%** | **100.0%**（20/20） | ✓ |
| 结构提案三次内通过率 | ≥ 98% | 100.0%（20/20） | ✓ |
| 槽位内容首次通过率 | ≥ 90% | 100.0%（100/100） | ✓ |
| 单章端到端成功率 | ≥ 90% | 100.0%（20/20） | ✓ |
| 单章平均耗时 | 记录，不设目标 | 平均 85.6s · 中位 83.3s · 最长 110.0s | — |

全库 `validation_failed` 计数为 **0**：这一批里没有任何一次提交被确定性校验拒绝过。

**但这四个 100% 掩盖了一件事**，报告现在会单独印出来：

> 1 个槽位有过「模型只说话、没调 `complete_assignment`」的 attempt（重试后成功）。

它按口径确实不进首次通过率的分母——没有提交，就谈不上「提交没通过」——
但只是把它剔掉，读报告的人会以为槽位这一侧一次意外都没有过。
这是 20 次实测**之后**补的一项统计，因为原来的报告在这一点上会说谎。
`121 个 execution 对 120 个 assignment` 是发现它的线索。

**这一批的样本局限见 §5**：20 次跑的是同一份输入，
所以它证明的是「稳定地处理**这一章**」，不是「稳定地处理章节」。

### 1.2 密集批次 — `chapter-packet-dense.txt`，连续 5 次

主批次的 20 次跑的是同一份输入，只能证明「稳定地处理**这一章**」。
所以另做了一份刻意更难的执行包：五个人物、五条情节要求，
其中两条互相拉扯——「四房的反应必须在**同一场**里全部呈现」（禁止拆场）
与「某人的沉默要在前面几场就被注意到、结尾才兑现」（强制跨场铺垫）。

| 指标 | 实测 |
|---|---|
| 结构提案首次通过率 | 100.0%（5/5） |
| 结构提案三次内通过率 | 100.0%（5/5） |
| 槽位内容首次通过率 | 100.0%（32/32） |
| 单章端到端成功率 | 100.0%（5/5） |
| 单章耗时 | 平均 157.0s · 中位 158.7s · 最长 174.7s |

37 个 assignment 对 37 个 execution——**一次重试都没有**，
`validation_failed` 同样为 0。

**两批的结构对照**才是这一小批真正的产出：

| | 简单包 ×20 | 密集包 ×5 |
|---|---|---|
| 场景数 | 3（20 次**全部**） | 4–5 |
| 槽位数 | 6 | 7–8 |
| 产物大小 | 9.6 – 13.5 KB | 22.6 – 27.3 KB |
| 耗时 | 85.6s | 157.0s |

结构 Agent 对着更密的素材切出了更多场景、写出了两倍长的正文。
这说明 S2 的「场景数由素材密度决定，不预设固定值」是一条**真的被执行了**的判据，
而不是一句正好合身于简单包的话——如果它是废话，密集包应该照样切 3 场。

**一处需要如实记下的差异**：密集包的场景数在 4 与 5 之间摆动（3 次 4 场、2 次 5 场），
不像简单包那样 20 次全一致。这是素材本身的合理歧义（那五条情节要求
既能压进四场也能摊成五场），不是不稳定——但它意味着**结构不是可复现的**。
对内容生产没问题，如果将来有人指望「同一份输入必然得到同一棵结构」，
这个预期要在那时被明确否掉。

## 2. 统计口径

这一节比上面那张表更重要：**同一批数据换个口径能差出十几个百分点**，
所以口径必须先说清楚，且与 `measure-runs.ts` 的实现一字对应
（改口径要同时改那份文件的头注释）。

**一次「提交」= 一条 `assignment_submitted` trace，不是一次 Execution。**

这是 D-20 带来的直接后果：被确定性校验拒绝**不收敛 execution**，
模型可以在同一次 Assignment 里改完再交。所以一次 execution 可能包含多条提交。
如果按 execution 计数，「先错两次再改对」会被记成**首次通过**——
而那恰恰是首次没通过，是 M4 要测的那个失败。这一条有专门的回归测试守着
（`tests/integration/m4-metrics.test.ts`，反证过：把口径退化成按 execution 计，
对应用例立刻变红）。

各指标的分母：

| 指标 | 分母 | 剔除了什么 |
|---|---|---|
| 结构提案首次通过率 | 至少提交过一次结构的任务 | 一次都没提交到的（Provider 400、超时、模型只说话不调工具） |
| 结构提案三次内通过率 | 同上 | 同上 |
| 槽位内容首次通过率 | 至少提交过一次的槽位 | 同上 |
| 单章端到端成功率 | 本次实际跑的全部任务 | **不剔除任何东西** |

**为什么结构通过率要剔除「一次都没提交到」**：把它们算作「未通过」，
就是把「链路故障」和「模型交了但结构错了」混进同一个数字。
这两者的修法完全不同——前者改代码或配置，后者改 Skill 文本与 `agentHint`——
混在一起会让人拿着一个偏低的数字去改本来没问题的 Skill 文案。
被剔除的数量会在报告里单独印出来，不会被藏掉。

## 3. 调优过程

### L0 — 接线阶段（还没到调 Skill 就先挡住了）

M4 的第一次真实调用根本没走到结构校验，直接 `HTTP 400`：

```
Invalid schema for function 'complete_assignment':
schema must be a JSON Schema of 'type: "object"', got 'type: null'.
```

`complete_assignment` 是 6 个工具里唯一的判别联合，投影成 JSON Schema 时
少了根 `type`。补一行即可，但值得记下来的是**它为什么能活到 M4**：
M3 的 508 条测试全绿，而 `FakeProvider` 不校验 schema。
「adapter 已实现」与「adapter 能跑通」之间隔着一次真实调用。

文档 §12.2 把 M4 排在 UI 之前的理由（「观察它不需要 UI」）在这里第一次兑现——
若按常规顺序等界面建完再接真实模型，这个 400 会在所有界面工作做完之后才出现。

### L1 — Skill 文本与 Output Contract（D-17 规定的第一级手段）

四份 `SKILL.md` 从占位骨架改写为可用初稿。改动不是「写得更详细」，
而是针对**结构提案会怎么错**下手：

1. **`order` 与 `dependsOn` 分开讲，并给出反例。**
   这两个字段一个管阅读顺序、一个管生产顺序，是最容易混淆的一处。
2. **明确要求「标题槽位必须 `dependsOn` 章节骨架」。**
   这条来自第一次真实运行的观察：结构 Agent 给 `title` 配了 `dependsOn: []`，
   于是标题在骨架和所有场景之前就被写掉了——它要概括整章，却什么都还没看到。
   `order` 靠前和 `dependsOn` 靠后并不矛盾，这正是两个字段分开的原因。
3. **提交前自检做成清单，逐条对应校验规则**（单根、ID 正则、`order` 不重复、
   依赖不成环、不依赖容器、至少一个内容槽位……），而不是一句「请仔细检查」。
4. **`instruction` 的写法给了差/好对照**，并要求写全「发生什么、改变什么、停在哪里」。
   最后一项最容易漏，而它正是下游场景衔接上一场的唯一依据。
5. 场景 Skill 里把 `forbidPattern`（不得出现 Markdown 小标题）**原样写进自检清单**，
   因为它是唯一一条会硬性拒绝提交的正则。

不常用的内容（结构设计的常见失误、场景篇幅的增删办法）放进**非注入章节**，
靠 `read_skill_section` 按需取——注入进去只会稀释真正要遵守的那几条。

**L1 的效果是可归因的，不是「改完就好了」**。有一处能直接对照：

- 改之前（M4 第一次真实运行）：结构 Agent 给 `title` 配的是 `dependsOn: []`，
  于是标题在骨架和所有场景之前就被写掉——它要概括整章，却什么都还没看到。
- 改之后：20 次全部是 `title → dependsOn: [章节骨架]`。

`title` 这一处是**干净的归因**：规则写进 S3 之前是 `dependsOn: []`，写进去之后 20/20。

结构稳定性那一处**不构成归因，只能算观察**：改之后 20 次全部是 6 槽位 / 3 场景。
改之前只有一次真实运行（4 个场景），n=1 撑不起「Skill 改动让场景数收敛到 3」
这种因果说法——两次之间除了 Skill 还差着一个 400 修复和整批采样。
能说的只是：改之后，同一份素材被反复读成同一个切分。

S2 真正的证据在 §1.2 的**跨输入对照**（简单包 3 场 vs 密集包 4–5 场），
那是同一份 Skill 面对不同素材的反应，不受上面这个混淆因素影响。

### L2 / L3 / L4 — **未启用**

D-17 规定按 L1→L4 顺序尝试，不得跳级。L1 之后主批次四项指标全部达标，
因此 **L2（砍结构复杂度）、L3（换更强模型）、L4（文本 JSON 兜底）一律没有动用**。

这三级留在原地，连同 §4.2 记下的那件事：真要用 L3，目标模型是
`deepseek-v4-pro`，不是文档原文的「推理型号」。

## 4. 顺带查实的两件事

### 4.1 REQ §13 的脱敏不再是纸面承诺

拿真实 API Key 跑完一整个任务后，对整个数据库做了一次**全表全列**扫描，
检索 Key 的值、`Authorization`、环境变量名 `DEEPSEEK_API_KEY`、`reasoning_content`
四项 —— **命中 0**。

这条保证的实现方式是 `shared/trace.ts` 的写入期键名黑名单（命中即解析失败），
而不是读取侧过滤。`cli/dump-trace.ts` 因此可以直接打印 payload，
并且**必须**直接打印：在读取侧再过一遍，等于承认库里可能有脏数据。

### 4.2 D-17 的 L3 按字面执行是空操作

DeepSeek 现在的 `/v1/models` 只有 `deepseek-v4-flash`、`deepseek-v4-pro`、
`deepseek-v4-flash-vision-exp`。旧名 `deepseek-chat` 与 `deepseek-reasoner` 都还能调，
但**两者都解析到同一个 `deepseek-v4-flash`**（实测：请求 `deepseek-reasoner`，
响应里的 `model` 字段回的是 `deepseek-v4-flash`）。

也就是说，L3 若按原文执行——「切到推理型号」——换来的是同一个模型，
通过率一点不会变，而且不会有任何报错。一个看起来生效、实际什么都没做的缓解手段
比没有这个手段更糟：它会让人误判「L3 试过了，该上 L4 了」，
而 L4 是文档自己标明「设计上的让步」的那一级。

已把 L3 的目标模型改为 `deepseek-v4-pro`，并加进 `providers.yaml` 的 `models` 列表
（别名解析在加载期校验模型是否在列表里，不加进去 L3 根本配不出来）。

**未实测**：`deepseek-v4-pro` 的价格与延迟。真要动用 L3 之前得先确认
「结构步骤变慢、变贵」这个代价能接受到什么程度。

## 5. 结论

**M4 的硬闸门通过：结构提案首次通过率 100%（20/20），门槛是 80%。**
两批合计 25 次真实运行、157 个 assignment，`validation_failed` **一次都没有**。
按 §12.2 的判据，可以进入 M5。

D-17 事先标注的风险——「DeepSeek 在长、深、带交叉引用的结构化 tool call 上
稳定性弱于第一梯队，80% 存在达不到的实际可能」——**没有兑现**。
L1（Skill 文本与 Output Contract）之后即达标，L2/L3/L4 一级都没用上。

### 这个数字有多可信

必须连着限制一起读，否则它会被当成比实际更强的证据：

1. **样本是两份输入，不是两份输入的分布。** 20 次同输入之间的差异只来自模型采样；
   真正的多样性来自素材本身。密集包证明了「更密 → 更多场景」这个方向是对的，
   但两份输入撑不起「对任意执行包都稳」这种说法。
2. **模型不是固定的。** `deepseek-chat` 是服务端别名，今天解析到 `deepseek-v4-flash`
   （见 §4.2）。DeepSeek 换掉这个别名指向的型号，这批数字就作废，
   而且**不会有任何通知**。这个数字带日期是有意义的。
3. **口径本身是被测过的**（`tests/integration/m4-metrics.test.ts`，8 条）。
   最关键那条做过反证：把口径退化成「按 execution 计」，用例立刻变红。
   这一点值得单独说——一个没被测过的通过率，和没有通过率差不多。
4. **报告一度在说谎，已修。** 主批次原本印的是四个干净的 100%，
   而实际有一个槽位的第一次 attempt 模型只说话没提交。
   剔除它是对的（没有提交就谈不上提交没通过），隐瞒它不对。

### 已知缺口，不阻塞 M5

- **`executions` 的 token 用量恒为 NULL**（Q-18）。整条链路建好了，
  但提交发生在工具调用内部、`usage` 在流的末尾才到，时序上永远填不上。
  API DTO 已经在对外发这个字段。留给 M5——它紧挨 D-10 的条件 UPDATE，
  不适合在里程碑收尾时匆忙动。
- **`provider_health` 没有仓储**（M3 记录），重启即丢。同批处理。
- **`deepseek-v4-pro` 的价格与延迟未实测**。真要动用 L3 之前得先量。

### 给业务方审校 SKILL.md 时的三个提示

`SKILL.md` 是「由实现方产出初稿、业务方审校」的。审校时最该盯的三处：

1. **S3 里「标题必须 `dependsOn` 章节骨架」** —— 这条是从实际缺陷反推出来的，
   但它把标题的生产推到了最后。如果业务上希望标题先定、后面照着标题写，
   这条要反过来，而那意味着标题只能依据执行包来拟。
2. **S2 的「场景数由素材密度决定」** —— 实测下来它确实在起作用（3 场 vs 4–5 场）。
   如果业务上需要固定场景数，这里要改成硬性数量，代价是失去对素材密度的适应。
3. **场景 Skill 里的「用可见行动推进，不用心理解释代替事件」** ——
   这是一条**风格判断**，不是技术约束。它现在写得相当强硬（给了差/好对照），
   产出的正文因此偏向白描。如果目标读者群更吃心理描写，这一条要松绑。
