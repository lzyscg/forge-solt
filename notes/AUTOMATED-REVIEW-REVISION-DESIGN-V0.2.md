## 1. 实测结论：我们手里的到底是什么

一句话：**它今天的实际水平是「两类缺陷的探测器」，远不到「审核员」。**
（这是**现状**，不是**定位**——两者的区别见 §1.1，它决定了 D-28 怎么写。）

29 条盲测用例（16 正例 + 12 反例 + 1 文风对照），三种提问架构，同一个模型档位
（`deepseek-chat`，与产线写作同档）：

| 缺陷类型 | 捆绑问四条 | 拆开单问 | 强制对账 |
|---|---|---|---|
| D1 承接断裂（首段接不上上一场） | 3/3 | **3/3** | — |
| D2 心理解释代替事件 | 3/3 | **3/3** | — |
| D3 事实矛盾（同一物件前后换名） | 0/3 | 0/3 | 0/3 |
| D4 停错地方（没停在槽位目标指定的位置） | 0/3 | 0/3 | 0/3 |
| **误打回（16 条真实产物）** | **0/16** | **0/16** | **0/16** |
| 文风对照（别扭但合规） | PASS | PASS | PASS |

三条必须刻进设计的事实：

1. **D1/D2 在三种架构下都稳定命中** → 这两条是真信号，不是提问方式的产物。
2. **D3/D4 在三种架构下都稳定为 0** → 这是能力边界，不是提示词没调好。
   失败方式已经查清：模型**做了对账、做对了、把矛盾写进自己的工作区、然后照样盖章**
   （neg-16 的清单里写着「正文里的说法：凭证、欠条、布包」，紧接着填 `一致: true`）。
   **不是感知失败，是判决失败**——这一档模型有极强的 PASS 先验。
3. **零误打回被三次独立实验确认** → 这是它敢无人值守跑起来的前提。
   但它与 PASS 先验是同一枚硬币：**这个探测器只会漏，几乎不会冤。**

由此推出本设计最重要的一条约束：

> **「审核通过」的真实含义是「没撞上任何一条判据」，不是「写得行」。**
> 系统的任何一处措辞（trace、UI、API 字段名）都不许把前者说成后者。
> 这是项目规矩「错误消息不能撒谎」在功能命名上的延伸。

### 1.1 实测告诉我们「它现在做得到什么」，不是「它该做什么」

以上是一次**能力测量**，不是一份**职责定义**。审核 Agent 的职责是
**找出生成内容里的错误**——这个职责不因当前能力不足而缩水。

因此本设计**不按实测结果裁剪判据**（D-28）：测出无效的判据照样上线，
它们的实测状态单独记录、单独跟踪。把一次能力快照写成产品规格，
正是 REQ §7 当年把 Slot Review 列为非目标时犯的错——我们现在要花整个 R0 去撤销它。

## 2. 目标与非目标

### 2.1 目标

- 槽位内容产出后，由审核 Agent **按判据找出其中的错误**。
  判据集合由审核 Skill 定义并持续迭代，**不由本设计冻结**（D-28）。
- 检出后自动返修，带着具体的、可验证的证据重做该槽位；
  返修时填槽 Agent 的上下文保持连续（D-31）。
- 全程无人参与判决（AC-014 不变：完成与否只由系统判定）。
- 返修有硬上限，任务**永不因审核卡死**。
- **每条判据的实测可靠度可被持续观察**——这样能力提升才有地方体现出来。

### 2.2 非目标（本版明确不做）

- **人工审核、人工批准、人工打回按钮**——业主已确认走全自动。
- **结构（Structure）返修**——本版只返修槽位内容。理由见 §10。
- **全局/跨场景审核、分段与综合**——一章约 10K token，远低于上下文上限，
  分段是为不存在的问题设计的机械。
- **把「审核通过」当作质量合格的凭据**对外暴露。

## 3. 核心形状

审核**不是**一个新的顶层流程，而是**槽位「完成」这个动作的一部分**。

```
槽位内容提交
   │
   ├─ FR-SLOT-004 确定性校验（现有，不变）
   │     失败 → 提交被拒，只写 trace（D-11/D-20，不变）
   │
   ├─ 内容落库，槽位进入 reviewing
   │
   ├─ 逐条判据各跑一次 review_slot execution
   │     │
   │     ├─ 全部 PASS ────────────────→ 槽位 completed
   │     │
   │     └─ 任一 REVISE
   │           ├─ finding 逐字引文校验（代码，非模型）
   │           ├─ 校验后无 finding 存活 → 视同 PASS，写 trace
   │           ├─ 返修轮次未耗尽 → 槽位回 pending，findings 进下一轮的
   │           │                     DeterministicContext
   │           └─ 返修轮次耗尽 → 槽位 completed，写 trace 记录「带病完成」
   │
   └─ 下游槽位才开始跑
```

**这个形状消灭了 V0.1 里一半以上的机械。** 关键在最后一行：
下游槽位永远只读到已审过的内容，因此**不存在级联返修**——
不需要 `repair_waves`、不需要修复波次调度、不需要「上游改了下游要不要重做」的判定。

## 4. 决策 D-21 … D-32

现有决策编号到 D-20，本版接续。

### D-21 审核判决只由系统采纳，模型只提供信号

模型返回 `verdict + findings`。**系统不直接执行模型的 verdict**：
它先做引文校验（D-25），再对照返修预算（D-26），最后由系统写定槽位状态。

*为什么*：AC-014 规定完成与否只由系统判定。审核若能直接翻转槽位状态，
就等于把判定权交给了模型。且实测证明模型的 verdict 在两类判据之外不可靠。

*拒绝的替代*：让模型返回「下一步该做什么」由引擎照做——那会让引擎的状态机
散落进提示词里，且模型一次幻觉就能让任务永久返修。

### D-22 审核是槽位完成的一部分，不是完成之后的事

槽位内容通过确定性校验后进入 `reviewing`，审核完成才可能进入 `completed`。
**下游槽位的依赖满足条件仍然是「依赖槽位 completed」，不需要改动。**

*已核对*：`src/server/domain/readiness.ts:192` 的 `blockedBy` 用
`byId.get(dep)?.status === 'completed'` 判定依赖满足，Ready 判定（同文件 §199 注释）
要求「全部依赖已 completed」。因此 `reviewing` 天然阻塞下游——
**调度逻辑一行都不用改**，这不是设计意图，是既有代码的现成性质。

*为什么*：这一条单独消灭了级联返修、修复波次、跨槽位一致性协调三大块机械。
它的代价是**每个开了审核的槽位都串行多出 N 次调用**（N = 判据数），
按实测约 4k 输入 token/次、约 1s/次，四条判据即每槽位 +16k token、+4s——可接受。

*拒绝的替代*：审核在整章产出后统一做（V0.1 的全局审核形态）。
那样必须回答「第 3 场改了第 5 场要不要重写」，而实测的探测器根本判不了这个。

### D-23 一条判据一次 execution

不把多条判据塞进一次调用。每条判据一次独立的 `review_slot` execution，
各自带完整上下文（执行包、骨架、上一场正文、槽位目标、待审正文），
system prompt 里只出现这一条判据，**不提示还有别的判据**。

*为什么*：实测（附录 §1）。捆绑提问下 6 条 REVISE 里 5 条是「每条判据恰好填一条 finding」
——模型在填表，finding 级精度只有 43%。拆开后 6 条里 4 条只有对口判据点火，
噪声消失。**召回完全一样，信噪比大幅改善**，代价 3.6x token（每槽位约 8k，可忽略）。

附带好处：每条 finding 天然携带它违反的判据 ID，返修指令可以直接对上，
不需要 V0.1 的证据坐标协议（D-44/D-52）。

### D-24 返修反馈走 DeterministicContext，不进冻结快照

AC-002 规定任务读自己那份冻结的模板/技能副本，永不读盘。
返修反馈是**任务运行期产生的数据**，与模板/技能无关，因此：

- 审核 Skill 本身**进冻结快照**（`task_skill_snapshots`，与写作 Skill 同等对待）；
- findings **进 DeterministicContext**，与「上一场正文」「章节骨架」同一层级。

*为什么*：这是 PROJECT-BRIEF §4 标红的第一个冲突（返修反馈在冻结快照里没有位置）的解法。
一旦认清 findings 是任务数据而非模板数据，冲突就不存在——**AC-002 一个字都不用改。**

### D-25 finding 必须通过逐字引文校验才被采纳

每条 finding 带 `quote`。系统用**代码**校验 `quote` 是否出现在待审正文中：

- 比对前做标点归一化（全角/半角引号、空白）。
  实测依据：21 条 finding 里 20 条逐字命中，唯一未命中的一条是模型把 `"` 写成了 `'`，
  定位本身是准的——不归一化会让有效率虚低 5 个百分点。
- 校验不过的 finding **丢弃**，写 trace 记录丢弃了几条。
- 若一次 REVISE 的 findings **全部**校验不过，**视同 PASS**（无从据以返修），写 trace。

*为什么*：实测（附录 §3）发现强制对账时模型给出的 6 条「依据」**没有一条**逐字出自正文，
全是转述，其中一条凭空编出了正文里没有的情节。引文校验是把幻觉挡在返修循环之外的
唯一低成本手段，而且它是**确定性的**——与 AC-014、D-21 同一条思路。

### D-26 返修预算耗尽后槽位照常完成，任务永不因审核卡死

每个槽位有 `revision_round`，上限来自 Slot Type 定义，**默认 2**。
耗尽后槽位以当前内容进入 `completed`，写一条明确的 trace 记录它是**带病完成**的。

*为什么*：审核当前只有两条判据实际生效，循环可能在它看不见的问题上反复通过；
更要紧的是，**一个永不终止的自动循环会烧光预算且没有人在看**。
本条保证任务终态可达——这是 AC-014「完成只由系统判定」的直接推论。

*拒绝的替代*：耗尽后把任务标 `failed`。审核检出的那点东西远不是产物可用性的全部，
为它作废整份产物，等于把一个「只会漏不会冤」的探测器当成质检员——
正是本文档反复警告的错误。

**同一条原则覆盖「审核自己挂了」**：`review_slot` execution 重试耗尽、
或返回的 JSON 解析不出 verdict 时，该判据记 `discarded`，槽位按未检出继续，
写 trace 说明是**审核失败**而非未检出问题。理由一致：
审核是一路附加信号，它的故障不该让内容生产停摆。
（R0.5 里 174 次调用 0 个解析失败，这条路径概率很低，但**不能没有**。）

### D-27 审核 Skill 按 Slot Type 可选绑定

`SlotTypeDefinition` 增加可选字段 `reviewSkillId`。未绑定的槽位类型**完全不走审核**，
一行代码都不执行。首版只给 `scene` 绑定。

*为什么*：实测只覆盖场景正文。给 `chapter_outline`、`title` 开审核没有任何证据支持，
而「默认全开」意味着为没测过的场景付 token 并承担未知误报。
这也让审核功能天然可以灰度——加一个 Slot Type 就是改一行模板。

### D-28 判据集合由审核 Skill 定义，设计不冻结它；实测可靠度**单独记录**

**审核 Agent 的职责是「找出生成内容里的错误」，不是「找出我们已经测出它能找的那几类错误」。**
判据的增删属于 Skill 层迭代，**设计文档不规定判据清单**，也不因当前能力不足而删减它。

首版审核 Skill 写**四条**判据（承接、可见行动、撞设定、停点兑现）。
其中两条实测有效、两条实测无效——**无效的照样带上**。

#### 为什么不按实测结果裁掉判据三/四

1. **实测数据本身支持带上它们**：D3/D4 的误报是 **0/16**。
   它们不是「会添乱」，是「什么都不做」。代价只有 token，没有错杀。
2. **删掉就再也测不到它们什么时候开始work**。模型换档、判据改写、Skill 迭代——
   任何一次改进的效果都需要生产数据来观察。判据不在线上，Q-28/Q-29/Q-30 永远只能靠离线实验回答。
3. **D-30 的措辞已经消化了这件事**：我们报的是「未检出问题」而不是「审核通过」。
   对一条什么都检不出的判据，「未检出问题」**字面上就是真的**。
   诚实性由措辞保证，**不需要靠删判据来保证**。
4. **把测量写成规格是本项目刚刚付过学费的错误**——REQ §7 当年把 Slot Review 写成非目标，
   我们现在要花整个 R0 阶段去撤销它。不要在同一份文档里新造一个。

#### 但必须同时记录的事实（这是本条的另一半）

「不裁剪判据」不等于「假装四条一样可靠」。以下事实进设计、进 Skill 注释、进 R4 的回归基线：

| 判据 | 实测（三种提问架构一致） | 状态 |
|---|---|---|
| 一 首段承接上一场结尾 | 召回 3/3，误报 0/16 | **已验证有效** |
| 二 可见行动而非心理解释 | 召回 3/3，误报 0/16 | **已验证有效** |
| 三 不与骨架/别的场次撞设定 | 召回 0/3，误报 0/16 | **在线但未验证有效** |
| 四 「停在哪里」必须兑现 | 召回 0/3，误报 0/16 | **在线但未验证有效** |

已排除的事：把判据三/四**写得更详细**救不回它们（附录 §2 的强制对账实验——
模型做了对账、把矛盾写进自己的工作区、然后照样盖章）。
**尚未排除**：为审核重写（而非照抄写作 SKILL）的判据、反转举证责任（Q-29）、
更强的模型档位（Q-30）。

*一条线索*：写作 SKILL 里判据二是唯一被写成「可判定规则」的
（「摄像机拍不到的就是解释」加差/好例子），而它正是测得最干净的一条。
判据的**写法**很可能还有空间。

*代价*：四条判据即每槽位约 16k 输入 token（两条是 8k）。按 D-23 的口径仍然可忽略。

### D-29 审核 execution 走同一条 active_execution_id 单车道

`review_slot` 与 `fill_slot` 共用 `tasks.active_execution_id`，一个任务同一时刻仍然只有
一个在跑的 execution。审核 execution 同样受 D-10 的 token 校验保护（UPDATE WHERE 里
带 `active_execution_id = e.id`），迟到的审核结果与迟到的写作结果走同一条拒绝路径。

*为什么*：不引入任何新的并发机械。D-10 的迟到结果防护、D-11/D-20 的提交闸门
是已经被反证过的资产，审核直接复用，**不需要为它重新证明一遍正确性**。

*代价*：判据无法并行，四条判据串行约 +4s/槽位。可接受；若将来成为瓶颈再单独立项。

### D-30 「通过」的措辞必须反映它的真实含义

trace kind、API 字段、UI 文案一律**不得**出现「审核通过」「质量合格」「已校验」这类
让人推出「内容质量有保障」的表述。

采用的措辞：**「未检出问题」**（`review_no_finding`）而非「审核通过」。
返修耗尽时：**「返修次数用尽，按现状完成」** 而非「审核完成」。

*为什么*：实测它只会漏不会冤，且四条判据里当前只有两条真的生效。叫「审核通过」会让使用者
（以及未来读代码的我们自己）推出一个数据不支持的结论。
项目规矩要求错误消息不撒谎；一个每次成功都在撒谎的功能名比错误消息更糟。

### D-31 槽位内 Agent 上下文连续，跨槽位不连续

**边界就是槽位。** 同一个槽位从首次生成到第 N 轮返修，填槽 Agent 看到的是一段
**连续的对话**：它自己的产出、它调过的工具与结果、审核意见，都还在。
换一个槽位则完全重来——不同槽位的 Agent 之间没有任何上下文传递。

返修那一轮的 `DeterministicContext` 因此包含：

1. 原有的确定性上下文（执行包、骨架、上一场正文、槽位目标）；
2. **上一轮 Agent 自己的对话轮次**——它的 `report_work`、它的 `read_slot` 调用与结果；
3. 上一轮提交的正文；
4. 通过引文校验的 findings（D-25）。

> **第 2 项是本条与 D-24 的差别所在**，也是本条真正的内容。
> 只带正文和意见，等于把稿子甩给一个没写过它的人去改。

#### 必须实现成「显式可复现的上下文」，不是「跨 execution 存活的会话对象」

这是本条的**实现约束**，不是措辞洁癖。上一轮的对话轮次要**序列化进
下一次 execution 的 `context_json`**，由它照常参与 `context_hash` / `prompt_hash` 计算。
四条理由：

1. **D-10** 的迟到结果防护建立在「1 execution = 1 个带 token 的工作单元」上。
   会话跨 execution 存活，token 校验就没有对应物。
2. **D-12** 的 `context_hash` / `prompt_hash` 存在的意义是可复现、可审计。
   真实输入若含「内存里攒的历史」，这两个 hash 就不再刻画输入。
3. **REQ §13**：`reasoning_content` 绝不许进任何 DB 列。
   因此**不能直接把 transcript 存下来**——序列化前必须剥掉隐藏推理，只留
   可见的 assistant 内容与工具调用/结果。这是一条硬约束，不是最佳实践。
4. **§8.6 重启恢复**：进程在审核中途挂掉，孤儿 execution 会被扫回 pending。
   内存里的会话对象没了，数据库里的显式上下文还在。
   **一个撑不过重启的连续性等于没有连续性。**

这样一来，`SlotContent = ContentAgent(SlotSkill, DeterministicContext, Slot)`
这个等式**一个字都不用改**——只是 `DeterministicContext` 多了一项，
与「上一场正文」处在同一层级。对模型它是连续对话，对系统它仍是纯函数。

*代价与已知风险*：`context_json` 随轮次增长（预算 2 轮 ⇒ 最多 3 稿，有界）；
上一轮的错误判断也留在上下文里，Agent 可能为自己的选择辩护而不是修改。

*为什么仍然接受这个风险*：**目前真正会触发返修的两类缺陷都是局部缺陷。**
判据一（首段接不上）与判据二（心理解释代替事件）**正确的修法就是定点改、别动其他**，
上下文连续带来的「锚定在原稿上、只做最小修改」在这两类上恰好是想要的行为。
判据三/四目前不点火（D-28），因此对返修行为暂无影响。

**这个判断有明确的失效条件**：一旦判据三/四开始生效，或新增了需要整段重写的判据，
锚定就从优点变成缺点——届时必须回到这一条重做判断。
Q-31 的实验正是为了让这件事可测，而不是靠回忆。

### D-32 审核 Agent 每轮全新，不带任何历史

与 D-31 相反：`review_slot` execution **不携带**上一轮的审核对话，也不携带
自己上一轮的 verdict。每一轮、每一条判据，都是一次干净的单次调用。

*为什么*（这条依据很硬）：**R0.5 的全部数字——D1/D2 的 3/3、16 条正例的 0 误报——
都是在单次、全新、无历史的调用下测出来的。** 一个带着「我上轮说过 REVISE」的审核 Agent
是一个我们从来没测过的东西，那些数字对它统统不适用。

而且失真方向明确：要么为上轮判断辩护而反复打回，要么因「上轮已提过」而放行。
考虑到实测出来的 PASS 先验本就很强，两个方向都是往坏处推。

**填槽连续、审核无状态**——这个非对称必须写进设计，不能靠实现者自觉。

## 5. 数据模型变更

### 5.1 新增表（一张）

```sql
CREATE TABLE slot_reviews (
  task_id       TEXT NOT NULL REFERENCES tasks(id),
  slot_id       TEXT NOT NULL,
  round         INTEGER NOT NULL,           -- 第几轮返修产生的这次审核，从 0 起
  criterion_id  TEXT NOT NULL,              -- 判据标识，来自冻结的审核 Skill
  execution_id  TEXT NOT NULL REFERENCES executions(id),
  verdict       TEXT NOT NULL CHECK (verdict IN ('no_finding','revise','discarded')),
  findings_json TEXT NOT NULL DEFAULT '[]', -- 仅存**通过引文校验**的 finding（D-25）
  created_at    TEXT NOT NULL,

  PRIMARY KEY (task_id, slot_id, round, criterion_id),
  FOREIGN KEY (task_id, slot_id) REFERENCES slots(task_id, slot_id)
);
```

`verdict` 三值的含义（与 D-25 对应）：
`no_finding` 未检出问题；`revise` 检出且至少一条 finding 通过引文校验；
`discarded` 模型判了 REVISE 但 findings 全部未通过引文校验，按未检出处理——
**单独取值而不是合并进 `no_finding`，因为这两件事在排查时含义完全不同。**

### 5.2 现有表的改动

```sql
-- slots：两列
ALTER TABLE slots ADD COLUMN revision_round INTEGER NOT NULL DEFAULT 0;
ALTER TABLE slots ADD COLUMN review_exhausted INTEGER NOT NULL DEFAULT 0
  CHECK (review_exhausted IN (0,1));   -- D-26：带病完成的标记

-- slots.status：增加 reviewing
--   ('pending','running','reviewing','completed','failed')

-- executions.operation：增加 review_slot
--   ('create_structure','fill_slot','review_slot')
```

#### 顺手加固 AC-009 的 CHECK

现有约束是单向蕴含，`reviewing` 带内容**不会**违反它：

```sql
NOT (status = 'completed' AND content_bearing = 1) OR (content 与 producer 齐备)
```

但它也因此**没有约束 `reviewing`**——而按 D-22，`reviewing` 的含义正是
「内容已提交、等待审核」，同一条不变量本就该成立。改为：

```sql
NOT (status IN ('completed','reviewing') AND content_bearing = 1) OR (...)
```

零成本，且能挡住「进了 reviewing 却没有内容」这类实现错误。

#### ⚠️ 现有 UNIQUE 约束会直接撞车（本版必须一并改）

`executions` 上有：

```sql
UNIQUE (task_id, target_slot_id, attempt_number)
```

`review_slot` 的 `target_slot_id` **就是被审的那个槽位**。于是同一槽位的
`fill_slot` attempt 1 与 `review_slot` attempt 1 会直接撞唯一键——
**不改这一条，R2 一跑就炸。**

该约束的原意（见 001 迁移里的注释）是锁住 `fill_slot` 这条槽位生产主路径的重试唯一性。
改为把 operation 纳入键：

```sql
UNIQUE (task_id, target_slot_id, operation, attempt_number)
```

同一轮里每条判据各有一次 `review_slot`，靠 `attempt_number` 区分不合适
（它们不是彼此的重试）。因此**审核 execution 的 `attempt_number` 只用于它自己的
provider 重试**，判据身份记在 `slot_reviews.criterion_id`，
各判据的 execution 通过 `context_json` 区分、由 `slot_reviews` 的主键保证不重复。

#### 返修**不消耗** `attempt_number` 与 `maxRetries`（D-26 补充）

`attempt_number` 与 D-06 的 `maxRetries` 计的是**同一份工作因故障重试**；
返修是**带着新输入做一份新工作**。两者混用会让 `maxRetries` 被返修轮次吃掉——
返修两轮之后，真正的故障重试预算就没了。

所以：每一轮返修**开一条新的 attempt 序列**，轮次单独由 `slots.revision_round` 计。

### 5.3 状态机改动（已核对现有代码）

`src/server/domain/state-machine.ts:153` 的 `SLOT_TRANSITIONS` 现有四行。
新增 `reviewing` 一行，并新增三个 `SlotAction`：

| from | action | to | 说明 |
|---|---|---|---|
| `running` | `commit_for_review` | `reviewing` | 绑定了审核 Skill 的槽位走这条 |
| `running` | `commit` | `completed` | 未绑定的走原路，**一个字不改** |
| `reviewing` | `review_clear` | `completed` | 未检出问题，或预算耗尽按现状完成 |

| `reviewing` | `cancel` | `pending` | 用户 stop 与孤儿恢复必须在审核期同样有效（AC-011） |

> 迁移表是 `(status, action) → status` 的纯函数，它不知道也不该知道槽位类型。

### 5.5 新增 trace kind（四个）

## 6. 引擎路径

现有引擎的「下一步该做什么」判定增加一个分支，**其余不动**：

```
若 槽位.status = 'reviewing'
   且 存在该轮尚未审的判据 C
   → 下一步 = review_slot(槽位, 判据 C)

若 槽位.status = 'reviewing' 且 本轮判据已全部审完
   → 系统结算（纯函数，domain 层）：
        任一 revise 且 revision_round < 上限
             → 槽位回 pending，revision_round += 1
        任一 revise 且 revision_round >= 上限
             → 槽位 completed，review_exhausted = 1，写 trace
        否则 → 槽位 completed
```

结算是**纯函数**，放 domain 层，享受 100% 分支覆盖的强制。
它的输入是本轮各判据的 verdict 与 `revision_round`，输出是目标状态——**零 IO**。

### 6.1 返修那一轮的上下文装配（D-31）

返修的 `fill_slot`，其 `DeterministicContext` 在原有四项之外追加：

| 追加项 | 来源 | 备注 |
|---|---|---|
| 上一轮 Agent 的可见输出 | 上一次 execution 的记录 | **必须先剥掉 `reasoning_content`**（NFR-005 / FR-AGT-005） |
| 上一轮读过哪些依赖槽位 | 只存**槽位 ID**，内容在装配时从库里现取 | 见下方 |
| 上一轮提交的正文 | `slots.content_text`（返修前的值） | 回 pending 时**不清空**内容列，否则上一稿就丢了 |
| 通过校验的 findings | `slot_reviews.findings_json` | 带判据 ID + 引文 + 问题说明 |

> **一个容易写错的地方（已核对代码，修正了本文档的早期说法）**：
> `SlotRepo.resetToPending` 的 SQL 里带 `AND status = 'running'`。
> 因此它**不能**被复用来做 `reviewing → pending`——复用的话它会静默地
> 一行都不改（`changes = 0`），槽位卡在 `reviewing`。
> 好在它是**安全失败**：不会误删内容，只会不动。
>
> 两条路径的真实差别不是「清不清内容」，而是**有没有内容**：
> `running` 的槽位从来没有内容（内容由 `commitContent` 写入，同时置为完成），
> 所以 `resetToPending` 根本不需要清；而 `reviewing` 的槽位**有上一稿**，
> 返修必须原样留着它。
>
> 实现要点：新增一个独立的仓储方法，WHERE 里带 `AND status = 'reviewing'`，
> **不触碰 `content_text` 与 producer 列**。不要给 `resetToPending` 放宽状态条件——
> 那条 `AND status = 'running'` 同时还在保护「已完成的槽位内容永不被重置」
> （FR-LIFE-004 / AC-012）。

> **不要给工具结果做副本**（改权威文档时从 FR-CTX-005 学到的）。
> `read_slot` 的返回本来就是库里的槽位内容——存副本既会与权威内容漂移，
> 又白白撑大 `context_json`。**只记「读过哪些槽位」，内容装配时现取。**
> FR-CTX-005 的判定标准是「清空进程内存后，只凭数据库与冻结快照能重建出
> 逐字相同的上下文」——现取满足它，副本反而制造了第二个真相来源。

装配本身是纯函数：给定上一次 execution 记录 + 本轮 `slot_reviews` 行 + 当前槽位内容
→ 新的上下文。剥离 `reasoning_content` 也在这一步，
且**必须有一条反证过的断言守住**（AC-R-014）。

## 7. 验收标准

- **AC-R-001** 未绑定 `reviewSkillId` 的槽位类型，产出后不产生任何 `review_slot` execution。
- **AC-R-002** 绑定后，每条判据恰好产生一次 execution，且 system prompt 中不含其他判据文本。
- **AC-R-003** 引文校验不通过的 finding 不得进入 `slot_reviews.findings_json`，
  也不得进入返修的 DeterministicContext。
- **AC-R-004** 一次 REVISE 的 findings 全部校验不通过时，槽位不进入返修，
  `verdict` 记为 `discarded`。
- **AC-R-005** `revision_round` 达到上限后，槽位必须进入 `completed` 且
  `review_exhausted = 1`；任务不得因此进入 `failed` 或永久 `running`。
- **AC-R-006** 迟到的 `review_slot` 结果（execution 已非 active）必须被拒绝并写
  `late_result_rejected`，与 `fill_slot` 走同一条路径。
- **AC-R-007** 下游槽位在上游槽位 `reviewing` 期间不得开始执行。
- **AC-R-008** 审核 Skill 必须来自冻结快照；改盘上的审核 Skill 不影响在跑任务（AC-002）。
- **AC-R-009** 返修产生的每一次状态变更都写 trace（Q-22 契约）。
- **AC-R-010** 系统任何输出中不得出现「审核通过」「质量合格」等表述（D-30）；
  以一条断言全文匹配的测试守住。
- **AC-R-011** `review_slot` execution 重试耗尽或返回无法解析时，槽位必须继续推进，
  不得停在 `reviewing`，也不得进入 `failed`。
- **AC-R-012** 审核期间用户 stop / 重启恢复扫到孤儿 execution 时，
  槽位从 `reviewing` 回到 `pending`，内容与 producer 不写（AC-011 语义在审核期同样成立）。
- **AC-R-013**（D-31）返修轮的 `context_json` 必须包含上一轮 Agent 的对话轮次与上一稿正文；
  从库里读出该 execution 即可完整复现它的输入，**不依赖任何进程内状态**。
- **AC-R-014**（D-31 / REQ §13）返修上下文中不得出现 `reasoning_content`。
  断言必须先用一条**带隐藏推理的真实响应**看着它失败，再看它通过。
- **AC-R-015**（D-31）`review_revise`（reviewing → pending）后，`content_text` 与
  producer 各列必须**原样保留**——下一轮上下文要用它。
  同时断言 `resetToPending` 对 `reviewing` 槽位返回 `changes = 0`（它带
  `AND status = 'running'` 守卫），确认两条路径没有被实现者合并。
- **AC-R-016**（D-32）`review_slot` 的 prompt 中不得包含任何往轮审核记录或往轮 verdict。
- **AC-R-017** 返修不得增加 `attempt_number` 的消耗：连续两轮返修后，
  该槽位仍有完整的 `maxRetries` 故障重试预算。

> **规矩 3.4**：以上每一条都必须**通过破坏产品代码来反证**——
> 断言必须先看着它失败。AC-R-005 与 AC-R-010 尤其容易写成装饰性测试。

### 9.1 R4 的回归基线

复用 R0.5 的用例（`probe/cases.json`，29 条，不用重造）——**这是唯一能证明
「实现出来的东西和实测的东西是同一个」的办法**。

分成两类指标，**含义完全不同，不许合并成一个数**：

| 类别 | 判据 | 要求 | 性质 |
|---|---|---|---|
| **门槛** | 一、二 | 召回 3/3 | **不达标就不能发** |
| **门槛** | 全部四条 | 16 条正例误报 = 0 | **不达标就不能发** |
| **基线** | 三、四 | 当前 0/3 | **记录，不设门槛**——这是要去超越的数，不是要去满足的数 |

第三行是 D-28 的落点：**把测不出来的判据留在线上，它的 0/3 就变成了一条可跟踪的基线。**
往后每一次审核 Skill 迭代、每一次模型换档，都拿同一批用例重跑，看这个数动没动。
判据若被裁掉，这条基线就不存在，改进也就无从证明。

> 这条回归应当固化成可重复执行的脚本（`probe/run-split.mjs` 已经是雏形），
> 而不是一次性的手工验证。

> **R3 单独成阶段是有意的。** 上下文连续性是唯一一处「模型行为」与「系统不变量」
> 直接接触的地方（`reasoning_content` 剥离、上一稿保留、执行可复现）。
> 把它混进 R2 会让一个本来就不小的 diff 变得没法审。

## 11. 未决问题

现有开放问题编号到 Q-27，本版接续。

- **Q-28 审核判据的写法还有多少空间？**
  R0.5 的判据是照抄写作 SKILL 的，不是为审核写的。已知：判据二（唯一写成「可判定规则」
  加差/好例子的那条）测得最干净。已排除：把判据三/四写详细救不回它们。
  未测：为审核重写的判据能否覆盖尚未注入过的缺陷类型（节奏、人物声音一致性、信息重复）。
  **前置条件是用例——每加一个判据就得配一类注入缺陷的用例，否则无从判断新判据是在抓东西还是在幻觉。**
  这是 Skill 层迭代，不阻塞 R0–R3。

- **Q-29 「默认 REVISE、必须逐字举证才判 PASS」能不能救回判据四？**
  线索：强制对账时那 6 条误判为「已兑现」的依据，**6 条全是转述、无一逐字出自正文**。
  若反转举证责任并用 `includes` 校验证据，这 6 条会被机械拦下。
  预测（供证伪）：**对 D4 有戏，对 D3 没戏**——D3 的模型摘录（凭证/欠条/布包）确实逐字在正文里，
  过得了校验，而代码判不了这仨是不是同一样东西。
  必须同时测误报会不会从 0 顶上去。用例现成，一次实验即可。

- **Q-30 更强的模型档位值不值得为审核单独付费？**
  全部结论只覆盖 `deepseek-chat`（v4-flash）。建议**等 V0.2 落地、跑出真实返修数据之后再评估**，
  而不是现在为它扩范围。

- **Q-31 上下文连续到底让返修变好了多少？**
  D-31 的收益目前是**推理，不是实测**——「稿子由写过它的人来改会更好」听着对，
  但本项目的规矩是断言要能被反证。
  可测：拿 R0.5 的 6 条能被检出的反例（D1×3、D2×3），各跑两种返修
  ——(甲) 带上一轮对话轮次，(乙) 只带上一稿正文 + findings——
  比较修完之后**再审一次是否转为「未检出」**，以及**改动幅度**
  （甲若真的更「定点」，其 diff 应当明显更小）。
  这也是唯一能证伪「上一轮的错误判断会让它为自己辩护」这条已知风险的办法。
  **不阻塞 R0–R4**：先按 D-31 实现，测出来若 (乙) 不差，再回来简化。

- **Q-25（存量）** UX §13.5 的范围——本版新增 `reviewing` 状态与返修轮次的展示需求，
  可一并定案。

## 12. 这份设计的诚实声明

本设计交付的**不是内容质量保证**，是**一个按四条判据找错的审核 Agent，
其中两条经实测有效、两条尚未验证有效**。

它会可靠地修好接不上和干巴说明；对其余一切，它多半会说「未检出问题」，
**包括那些其实有问题的**。这是当前的能力水平，不是本设计的规格——
规格是「找出生成内容里的错误」，能力会随 Skill 与模型迭代往那个方向走（D-28）。

两句话必须同时成立，缺一不可：

- **不因为它现在做不到，就不让它做**——判据不裁剪，能力提升才有地方发生（D-28）。
- **不因为它在做，就说它做到了**——措辞只报「未检出问题」，绝不报「审核通过」（D-30）。

第一句管的是**别把天花板焊死**；第二句管的是**别把地板说成天花板**。
只要两句都守住，它就是个诚实、便宜、可以无人值守跑、并且**能被看着变好**的部件。
一旦哪里把它说成「质量已审核」，它立刻变成比没有审核更糟的东西——因为它会让人停止检查。
